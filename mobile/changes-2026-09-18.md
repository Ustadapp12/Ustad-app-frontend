# Changes 2026-09-18

Follow-on to yesterday's 21 → 114 surah expansion.

## Fixed: the recommended-next jump landed in the wrong chapter for most surahs

`SURAH_TO_CHAPTER` maps a surah to the chapter holding its **first** level.
That was a fair approximation at 21 short surahs, where a surah rarely
outgrew a 30-node chapter. Across the whole Quran it isn't: **79 of the 114
surahs span more than one chapter**. Jumping to a surah's opening chapter when
the recommendation is partway through it drops the user nowhere near where
they left off — for Al-Baqarah (215 nodes) that's up to **7 chapters** away.

Added `chapterForLevel(surahNum, surahLevelIdx)`: the chapter holding one
specific level. Plain division works (`(surahFlatStart + levelIdx) /
NODES_PER_CHAPTER`) because chapters are cut on a level count — every chapter
holds exactly 30 levels, and a season sign takes an extra slot without
counting toward that total.

Verified by script against the real chunking: **all 4,744 levels, zero
mismatches** between what `chapterForLevel` predicts and the chapter that
actually contains that level. Search jumps (which target level 0) agree with
`SURAH_TO_CHAPTER` for 114/114 surahs, so that path is unchanged.

Wired into the three places that move the viewport to the recommendation:

- **`jumpToRecommended`** (Home-tab tap, and after finishing a level) now
  resolves the recommendation's real chapter from its `lesson_group_id`'s
  position inside the surah. Its cross-chapter branch used to land at the new
  chapter's *top* and stop — fine when the curriculum was four chapters, but
  across 159 it usually leaves the recommended node off-screen. It now hands
  off to the pending-jump effect, which scrolls onto the node itself.
- **The cold-start "follow the recommendation into its chapter" effect** is now
  keyed on the resolved chapter, not just the surah. A recommendation's chapter
  is only knowable once that surah's levels have been fetched: on a cold start
  the first answer available is just "somewhere in this surah" (its opening
  chapter), and once the levels land a mid-surah recommendation resolves to its
  real chapter and needs correcting. Keyed on the surah alone, that correction
  never fired.
- `chapterForRecommended()` falls back to the surah's opening chapter while its
  levels are still unknown, so there's never a wrong-looking jump, just a less
  precise one that self-corrects.

The search jump and the recommendation jump now share one mechanism
(`pendingJump`), replacing the search-only `searchJumpSurah`. It carries an
optional `groupId`: set, it targets that specific level (the recommendation);
null, it targets the surah's opening level (search). The effect waits on the
target node's existence rather than trying to guess when the chapter switch and
the id-resolving fetch have both landed — the node can only exist once the
right chapter has laid out, so its presence *is* the readiness test.

## All 114 surahs are reachable and startable, with no readiness list in the app

Every surah in search is tappable, jumps to its first level on the map, and
offers to start it. Nothing in the app now carries any notion of which surahs
are "ready".

This replaced the approach from earlier in the day, where the app read a
backend-supplied enabled list and drew everything outside it as locked. That
was removed entirely — `utils/enabledSurahs.ts` is deleted, and no screen
imports `isMvpSurah`/`MVP_SURAH_NUMBERS` any more. Predicting availability from
a list meant the app had to be told what was ready; answering it at the tap, off
what the backend actually returns, means it never has to be told anything. As
content lands, surahs simply start working — no release, no constant to bump,
no second source of truth to drift.

What this rests on, checked in the backend rather than assumed:
`get_first_levels_for_surahs` (the batched endpoint the map uses to draw node
statuses) has **no content gate at all** — it reads lesson groups directly, and
those exist for the whole Quran (3,186 groups; Al-Baqarah has 143 with correct
2-ayah spans). So the map shows real, correct statuses for all 114 surahs
today. Only `get_levels_for_surah` and `start_session` carry the
`404 "Surah not in MVP catalogue"` gate.

So `fetchPhase` no longer filters by readiness either — filtering would have
replaced real data with placeholders for no benefit.

Where a tap genuinely can't resolve a lesson to open, the map says so (a Lumo
message beside the node) instead of leaving the tap dead or, worse, navigating
into a session for a group that doesn't exist. Its wording covers both causes
it can't tell apart — a dropped request and content that isn't served yet — so
it never wrongly claims a surah is unavailable:

> Couldn't open {surah} just now. Please try again!

## What today's behaviour actually is, end to end

Tracing surah 2 (Al-Baqarah) as it stands right now:

1. Search lists it, tapping offers **"Start Al-Baqarah?"** ✓
2. Confirming jumps the map to chapter 150 and scrolls onto Al-Baqarah's first
   node ✓
3. That node shows a real status, because the first-levels endpoint serves it ✓
4. Tapping it resolves a real group and opens the start card with its real ayah
   range ✓
5. Pressing **Start** calls `start_session`, which 404s today → the lesson
   screen's existing error path alerts and returns to the map

Step 5 is the only gap, and it closes with no app change the moment
`word_audio_ready` is set for the remaining 93 surahs (or that flag is dropped
from `_ENABLED_SURAH_FILTER`), the `content:enabled_surahs` Redis key is
busted, and the content refactor is committed and deployed — it's still
uncommitted in the working tree, HEAD unchanged at `952d474`.

## Session 2: verified the whole Quran against the testing backend, switched config to it

The backend's full-Quran work (`8ea74a3`) and streak calendar (`14762bf`) are
deployed to `ustad-app-backend-testing.vercel.app`. Verified against the live
deployment rather than assumed, with a real guest account driving the same
endpoints the app calls:

- Catalogue: all 114 surahs, `content_status.content_ready` true for every one.
- Lesson groups: every surah's normal-group count is exactly `ceil(ayahs/2)`,
  ayah coverage runs 1..N with zero gaps, and the review interleave is never
  more than 2 normal levels in a row.
- `start_session` succeeds on 14 sampled surahs including 10 that were 404
  the day before. Full lessons played end to end on Al-Baqarah, Ar-Rahman and
  An-Nas: every exercise type generated, completion saved, 3 stars, the level
  flips to `completed`.
- Audio: 339 full-ayah files and 225 word-audio files sampled across all 114
  surahs (first/middle/last ayah), zero failures.
- `GET /learning/streak/calendar` returns `{start_date, practiced_dates,
  frozen_dates}`, matching `types/api.ts`'s `StreakCalendar` field for field.

**Review levels were missing for the 93 newly-added surahs** and have now been
seeded backend-side. Before that, `SURAH_LEVEL_COUNT` expected 4,744 nodes
against the backend's 3,186, so `trustedLevels()` rejected 93 of 114 surahs
and only their first level was reachable. After seeding, 113 of 114 match.

**Al-Baqarah is the one that still does not**, and it is not a seeding
failure: `app/content/repository.py`'s `list_lesson_groups` reads
`to_list(length=200)`, and Al-Baqarah is now 215 docs (143 normal + 72
review). The API returns the first 200 and the surah stops at ayah 266, so
`trustedLevels` rejects it exactly as before. It is the only surah over 200
(next largest is Aal-i-Imraan at 150). A second cap in the same file,
`list_lesson_groups_for_surahs`'s `to_list(length=500)`, is latent but worse:
it caches per surah including the `{n: [] for n in missing}` pre-seed, so a
cold-cache batch overflowing 500 caches an empty level list for an hour.
Season batches top out near 497 docs; pull-to-refresh sends every loaded
phase at once and will overflow. Both are backend fixes, flagged not applied.

**Guest accounts never populate the streak calendar.** `complete_session`'s
day-log write sits inside `if not _is_guest(user)`, and `get_streak_calendar`
only adds today live when the state is frozen, never when practiced. So a
guest sees a streak number on the hero card above a permanently blank
calendar. Consistent with the documented "shown but not banked until signup"
guest rule, but worth knowing when testing, since first launch mints a guest.

**`src/config.ts` now points at the testing backend** (explicitly requested for
this build). Production stays commented out directly above it.
