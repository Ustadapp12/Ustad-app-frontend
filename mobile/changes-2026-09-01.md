# Changes — 2026-09-01

## MapScreen.tsx — glow on every open level, not just the recommended one

Every currently open (unlocked, not-yet-completed) map node now renders a
soft breathing halo behind its art, color-matched to what the node is:
bluish-gray (`colors.nodeLocked`) for a normal level, green (`colors.primary`)
for a special/review level. Applies to every open node regardless of status
(`current` / `available` / `pending`) — not only the one node the backend
recommends next, which keeps its separate "Begin/Continue here" tag exactly
as before. Locked nodes (nothing to invite the player toward yet) and
completed nodes (already have their own gold "pop" scale animation) are
unchanged.

The glow's opacity breathes by reusing the existing `goldAnim` shared value
(already looping continuously to drive the completed-node pop), so no new
animation loop was added per node.

New styles: `nodeGlowNormal`, `nodeGlowSpecial` in `MapScreen.tsx`'s
`makeStyles`. New render logic in `MapNode`: `isOpen` + `glowOpacity`.

## MainTabs.tsx — removed insets.bottom padding from the tab bar

Real-device screenshot showed a persistent gray gap between the tab labels
(Home/Quests/Board/Profile) and the Android nav bar, present even sitting
idle with no swipe/back interaction. Traced the padding to
`tabBarStyle`'s old `height`/`paddingBottom` formula, which grew by
`insets.bottom` whenever it read nonzero. Confirmed via
`android/gradle.properties` (`edgeToEdgeEnabled=true`) that this app IS
edge-to-edge (RN's own `ReactActivityDelegate` calls `enableEdgeToEdge()`
whenever that gradle flag is set — contrary to `responsive.ts`'s
`safeBottomInset()` comment, which assumed otherwise), so `insets.bottom` is
a real, non-stale value on this device — meaning the padding was doing what
it was told, just for a nav bar the user says persists on screen and that
the app has its own swipe-down mechanism to reveal, so no reserved clearance
is wanted at all.

Per explicit user request ("I need NO PADDING its extra useless space,
decrease size of that tab bar"): stripped `insets.bottom` out of the tab bar
sizing entirely. `tabBarStyle` is now a flat `{ height: 64, paddingBottom: 0
}` (`TAB_BAR_CONTENT_H`), regardless of device/inset state. Removed the
now-unused `useSafeAreaInsets`/`safeBottomInset` calls and the
`TAB_BAR_PAD_BOTTOM`/`TAB_BAR_PAD_BOTTOM_NO_INSET` constants from
`MainTabs.tsx`. `safeBottomInset()` itself is untouched and still used by
the other ~27 screens that pad their own bottom-edge content — this change
is scoped to the tab bar only.

## RootNavigator.tsx / new ExitAppModal.tsx — custom exit-app popup

Replaced the native `Alert.alert('Exit app', 'Do you want to close the app?', ...)`
(hardware-back handler, fires only when the root stack has nothing left to
pop to) with the app's own modal, matching the Lumo-card style already used
by `StreakLostModal` and `LessonSessionScreen`'s exit-lesson confirm instead
of looking like a bare OS dialog. New component `src/components/ExitAppModal.tsx`:
Leave (red, left) / Stay (green, right) — per explicit user request. Leave
calls `BackHandler.exitApp()`; Stay just closes the modal. `RootNavigator.tsx`
now holds `exitConfirmVisible` state instead of calling `Alert.alert` directly.

## ProfileScreen.tsx / new utils/appVersion.ts — visible app version footer

Added a small `v1.0.28`-style label to the bottom of Profile, after a tester
(Dua) reported seeing stale content on a phone that reported the current
version — turned out the app had no in-app version display at all, so that
claim couldn't be checked without reverse-engineering it from an art asset.
`package.json`'s own `"version"` field was ruled out as the source (stuck at
`1.0.0` since 2026-08-21, silently wrong for every real build since). Instead
`APP_VERSION` reads `process.env.VERSION_NAME` — the same env var already set
by hand before every release build (see `versions.md`/build guide) — inlined
to a literal string at Metro-bundle time via a new
`babel-plugin-transform-inline-environment-variables` devDependency
(`babel.config.js` plugins list). Can't drift from the real native
versionName the way a separately-tracked constant could.

**Install gotcha, since neither `babel.config.js` nor `package.json` live
under `src/`/`assets/`:** the standard robocopy sync (Step 1 of the build
guide) does NOT cover either file. Both need a one-time manual sync/install
into `C:\BuildProjects\ustadapp-mobile\` — done for the 1.0.28 build below,
but any FUTURE edit to `babel.config.js` needs the same manual copy, same as
native `android/`/`ios/` edits already do.

## MapScreen.tsx — node-glow shrunk, AppState foreground-refresh added, feedback FAB

Three separate changes, all in the same file:

- **Glow tightened** (user: today's earlier glow "too ugly and too big"):
  `nodeGlowNormal`/`nodeGlowSpecial` shrunk from 1.4x/1.75x of `NODE_SIZE`
  down to 1.14x/1.32x, background opacity and shadow both reduced to match —
  a close highlight ring instead of a diffuse halo. Added a small `1.06x`
  static scale on open nodes' own `Animated.View` so they still read as
  highlighted with the smaller glow.
- **AppState foreground-refresh** (real bug, reported live): MapScreen only
  mounts once for the app's lifetime, and the only refresh-on-return effect
  that existed was gated on `lastVisitedSurah` — set exclusively by
  `completeSession`/`abandonSession`. A plain background-to-foreground
  reopen with no lesson in between hit no refresh path at all, so
  `fullLevels`/`recommended` could sit stale indefinitely — reported as a
  "Continue here" tag landing next to a node that still rendered locked,
  self-correcting only on a manual pull-to-refresh. Fix: a new
  `AppState.addEventListener('change', ...)` effect calls the existing,
  already pull-to-refresh-tested `handleRefresh()` on every
  background-to-active transition, reusing its `RefreshControl` spinner as
  the loading signal. Not yet confirmed against a real repro on-device — see
  `versions.md`'s 1.0.28 entry.
- **Floating feedback button**: new circular button, bottom-right above the
  Profile tab, fixed over the map (outside the `ScrollView`, so it never
  scrolls away). Outline message-bubble-with-lines SVG icon (not an emoji —
  user asked for something closer to a real feedback-icon reference image),
  46px, `colors.primary` background. `onPress` → `navigation.navigate('Feedback')`,
  same destination as Profile's own Feedback card, deliberately unguarded so
  guests can use it too.

## SplashScreen.tsx — slower status-message rotation

`SPLASH_MESSAGE_MS` (how long each "Loading… / Creating your world… /
Planting the trees…" message holds before fading to the next) raised from
1200ms to 2200ms — user said the sequence read as too quick to actually
read.

## LessonSessionScreen.tsx — verse number was missing on the two speak exercises

Every exercise card already showed "Surah X · Verse Y" via `ex.ayah_no`
except `read_ayah_and_speak`/`read_and_speak` (the two mic/recitation
exercises), which only showed "Surah X" with no verse number — an
inconsistency, not a deliberate omission (unlike `sequence`/`ayat_then_order`,
which genuinely span multiple ayahs at once and correctly have no single
verse to name). Added `· Verse {ex.ayah_no}` to both, matching every other
exercise type. Confirmed this also correctly covers the 4-ayah
special/revision levels: `ex.ayah_no` is set per-exercise by the backend's
exercise builders regardless of whether the group is normal or merged, with
no special-case branching on `isSpecial` for this label anywhere in the
frontend.
