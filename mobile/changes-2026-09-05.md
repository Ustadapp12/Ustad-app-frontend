# Changes 2026-09-05

## Local notifications — daily reminders, message randomization, app-name branding, dev test button

**Platform:** Both Android and iOS (Notifee is cross-platform), but only actually exercisable
today via iOS TestFlight production builds — Notifee no-ops entirely under `__DEV__`, so none
of this is testable on a Debug/Metro build on either platform.

- `LocalNotificationKind` extended: `daily_practice_reminder_10am`/`_5pm` (previously a single
  user-configurable `reminderHour` that always no-op'd — no picker exists yet — now hardcoded
  to fire at 10am and 5pm for every user, gated only on "already practiced today"), plus three
  new kinds defined but **not yet wired into any real trigger**: `inactivity_nudge`,
  `milestone_completed`, `streak_lost`. Their message arrays exist; no compute function
  schedules them yet.
- 4 message-template arrays (`STREAK_MESSAGES`, `INACTIVITY_MESSAGES`, `MILESTONE_MESSAGES`,
  `STREAK_LOST_MESSAGES`), 2 variants each, picked via a new `pickRandom()` helper so repeat
  notifications of the same kind don't read identically every time.
- Every notification title now gets an `"UstadApp: "` prefix via a new `withAppName()` helper,
  applied once at the scheduling call sites — user-requested branding, since the app name
  otherwise never appears in the message content itself (only in the OS's own icon/name
  alongside it).
- New `sendTestNotifications()` (TEMP, marked for removal before publishing) fires all 6
  in-use notification kinds 5 seconds apart, wired to a **"🔔 Test Notifications (dev only)"**
  button at the bottom of ProfileScreen — lets the real message content be previewed on a real
  device without waiting for real trigger conditions (10am/5pm/near-midnight/etc). Both the
  button and the function need removing before a real store submission.

## MapScreen — loading stutter, overscroll leak

**Platform:** Both platforms for the loading-order fix; iOS-only for the overscroll leak
(iOS's rubber-band bounce is what exposes it — Android doesn't overscroll the same way here).

- Added a `nodesReady` gate (`chapterResolved && !loadingPaths`) so the loading overlay now
  stays up until node data has actually arrived, instead of letting the SVG background render
  first and the nodes visibly populate afterward on top of it (reported: graph renders, "then
  they're formulated in front of me").
- Added an indeterminate animated loading bar + a temporary on-screen "Map loaded in Xms"
  badge — `console.log` output is unreachable when testing via TestFlight without a Mac, so
  timing has to be visible in the UI itself to be checked at all.
- Fixed a second overscroll-bounce color leak at the **bottom** of the map (a companion to an
  already-fixed top-edge seam from 2026-09-03): added a matching `colors.mapBg`-colored strip
  behind the ScrollView at the bottom edge, same fix pattern as the top one.

## MainTabs — iOS tab bar safe-area clearance (3 iterations to get right)

**Platform:** iOS only. Android's tab bar padding is untouched (still flat `0`, same as
before today) at every step below.

- Started as a hardcoded `paddingBottom: 16` for iOS on `tabBarStyle`. Replaced with the real
  `useSafeAreaInsets().bottom` (~34pt on notched iPhones) — still on `tabBarStyle`.
- User reported the bar now felt "TOOOO MUCH PADDING" — tried halving it
  (`insets.bottom * 0.5`).
- User then reported the tab labels ("Quests"/"Board" specifically — the two center tabs)
  were being visually cut by the iPhone's own Home Indicator pill, confirmed via screenshot
  and cross-checked against real iPhone 15 specs (34pt bottom safe area, Home Indicator owns
  a 21pt box within it — see sources in that conversation). Root cause: applying the
  clearance as `tabBarStyle`'s own `paddingBottom` grows the bar's *total height* but doesn't
  reliably reposition the icon+label content within it — every value tried just made the bar
  taller without moving the content away from the true edge, which is why "too much padding"
  and "words being cut" were both true reports about the same build.
- **Final fix:** moved the clearance to `tabBarItemStyle` (`paddingBottom: insets.bottom`),
  which applies directly inside each tab's own pressable box and reliably pushes its
  icon+label group up — a more direct lever than the outer bar's height/padding math.
  `tabBarStyle`'s own height now just grows by the full inset so the bar's white background
  still reaches the true edge with no gap.

## Three post-lesson/streak screens — background no longer depends on insets timing

**Platform:** iOS-specific in practice — Android's `safeBottomInset()` already returns `0`
(this app isn't edge-to-edge there), so a stale first-render inset value of `0` changes
nothing on Android; on iOS the real inset is ~34pt, so the same staleness leaves a real gap.

Affected: `StreakCelebrationScreen.tsx`, `LessonSummaryScreen.tsx`,
`StreakRepairProgressScreen.tsx`. All three sized their own `LinearGradient` background via
`paddingBottom: insets.bottom` directly on the gradient. `useSafeAreaInsets()` can report a
stale `0` on a freshly-pushed `'fade'` screen's very first render (a known React Navigation /
safe-area-context timing gap) — when that happens here, the gradient falls short of the true
bottom edge by the full inset, exposing the Stack Navigator's own fallback `contentStyle`
color (`#0D1B2A`) underneath. Reported as a "blue gradient leaking from below" / "wrong size."
**Fix:** split each screen into a full-bleed `LinearGradient` (`StyleSheet.absoluteFill`, zero
insets dependency, always covers the whole screen) as a background layer, with the actual
content in a separate inner `View` that still uses `insets.bottom` for its own clearance —
the background can no longer fall short regardless of insets timing.

## LessonSessionScreen — white screen between exercises (iOS-only)

**Platform:** iOS only, per the original report and its predecessor bug
(`daab740`, 2026-09-03) — Android's UI thread apparently keeps the previous frame painted
through the same mount cost, so the same gap never became visible there.

The 2026-09-03 fix for a 2-3s *frozen spinner* between exercises cleared the spinner
synchronously the instant `advanceFn()` was invoked, rather than waiting for the next
exercise to actually render. That made the frozen-spinner symptom go away, but for a mount
that's genuinely slow, clearing the spinner early doesn't make the next component paint any
faster — it just uncovers blank white for the same real duration instead. Reported today as
recurring ~6 times in a single level (i.e. on most question transitions, not only the final
one). Two-part fix:
- The **last exercise** (`result.done`, awaiting `completeSession()` — a real network
  round-trip with no next exercise to render) now explicitly re-arms `setSubmitting(true)` at
  the top of that branch, so the spinner stays visible through the whole request instead of
  leaving nothing on screen while it's in flight.
- Every **other** transition now clears the spinner via a `useEffect` keyed on
  `exercise?.ex_id`, which only fires once the new exercise has actually committed and
  rendered — tying the spinner's lifetime to a real "next exercise is on screen" signal
  instead of guessing the mount is fast enough not to matter.

## ProfileScreen — "Save and Close" button in the Arabic Font modal

**Platform:** Not platform-specific (a plain Yoga flex layout bug), discovered via iOS
testing. `modalCancel`'s `flex: 1` is correct when it sits beside `modalConfirm` inside
`modalBtns`' row layout (Logout/Delete modals) but breaks when reused standalone in a column
container (the Font modal) — the button rendered as an empty bordered box with the text
invisible/uncommitted. Fixed by overriding to `flex: 0, alignSelf: 'stretch'` for that one
usage only; the two row-context usages are untouched.

## Build pipeline — 3 real CI bugs found and fixed getting a fresh production build out

**Platform:** iOS EAS/TestFlight pipeline (`ios-testflight.yml`) specifically; one fix
(`android/build.gradle`'s Crashlytics classpath) is Android-only and unrelated to the other
two.

1. **`package-lock.json` out of sync under a different npm version.** Adding
   `@notifee/react-native` regenerated the lockfile locally under npm 11 (Node 24); CI's
   Node 22 runner bundles npm 10, which resolves one optional peer dependency
   (`@firebase/auth`'s optional peer on `@react-native-async-storage/async-storage@^2.2.0`)
   differently, and `npm ci` failed with EUSAGE. Reproduced locally with `npx -y npm@10 ci`
   before touching anything, fixed by regenerating under npm 10, reverified clean.
2. **`metro.config.js`/`babel.config.js` regression.** Earlier the same session both were
   switched to bare-RN-only config (`@react-native/metro-config`, `@react-native/babel-preset`)
   to quiet an unrelated local Debug/Metro warning — which silently undid a fix already
   shipped and documented in commit `b71258c` from the prior TestFlight session: `eas build`'s
   `expo export:embed` step requires Expo's own metro/babel config specifically. Build failed
   at "Bundle JavaScript build phase"; reverted directly to the known-good version. Both files
   now carry an explicit comment warning against repeating this swap.
3. **Build-number collision between the production and debug TestFlight pipelines** — see
   `project_ios_debug_testflight_loop` memory for the full writeup. `app.json`'s
   `ios.buildNumber` was still `"1"` (bumped to 2 on submit), colliding with the already-
   uploaded build 2 from the original 2026-09-01 submission; recurred a second time
   immediately after a one-time bump to 300, since the local-version-source bump is never
   persisted back to the committed file. Bumped again to 350 for headroom; a proper
   server-tracked ("remote") version source remains blocked on needing an interactive TTY
   prompt this environment can't provide.
4. **Also restored** `android/build.gradle`'s `firebase-crashlytics-gradle` classpath, found
   missing (pre-existing uncommitted state, unrelated to any of the above) while reviewing the
   diff before pushing — `app/build.gradle` still `apply plugin`s it, which would have broken
   the next Android build.
