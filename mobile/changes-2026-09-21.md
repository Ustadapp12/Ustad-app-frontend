# Changes 2026-09-21

## Fixed: `ios/Podfile.lock` locked to a pod that no longer exists in the project

Dependency audit flagged that `ios/Podfile.lock` pinned
`NitroAudioRecorderPlayer (4.5.0)` — the podspec name used by the
Nitro-architecture rewrite of `react-native-audio-recorder-player` — while
`package.json` has pinned `react-native-audio-recorder-player: ^3.6.0` (the
old bridge-based module, podspec name `RNAudioRecorderPlayer`) since
2026-07-03. This is the record button on every recitation exercise
(`ReadAyahAndSpeak`/`ReadAndSpeak` in `LessonSessionScreen.tsx`), core to a
Quran-recitation app, so this needed to be resolved carefully rather than
just papered over.

**Root-cause investigation (`git log -p -- mobile/package.json`,
`mobile/changes.md`):**

- `ios/Podfile.lock` was committed exactly once, in `014bfd8` ("iOS
  configurations added and ui simulation fixed", 2026-06-08) — generated
  correctly at the time against `react-native-audio-recorder-player@^4.5.0`
  (the Nitro version, matching `react-native-nitro-modules` also being a
  dependency then).
- `b11b3ff` ("fixing apk bugs, detail in changes.md", 2026-07-03) downgraded
  `package.json` to `^3.6.0` and dropped `react-native-nitro-modules`
  entirely. `changes.md`'s own 2026-07-02 session log (§6) confirms this was
  deliberate, not accidental: `src/services/audioRecorder.ts` was already
  written and wired against the *old* bridge API
  (`new AudioRecorderPlayer(); .startRecorder()/.stopRecorder()/
  .startPlayer()/.stopPlayer()/.addPlayBackListener()`), which is
  `react-native-audio-recorder-player` v3.x's class-based API, not the Nitro
  rewrite's. So `^3.6.0` in `package.json` is the intended, currently-used
  version, and the actual usage code already matches it correctly — there is
  no code-level mismatch to fix.
- `ios/Podfile.lock` was simply never regenerated after that downgrade —
  the only commit that ever touched it predates the downgrade by nearly a
  month, and nothing has touched it since (confirmed via
  `git log -- mobile/ios/Podfile.lock`).
- Same root cause, lower severity, also found drifted in the same lock file:
  `react-native-screens` (locked 4.25.1 vs npm-resolved 4.27.0),
  `react-native-gesture-handler` (2.31.2 vs 2.32.0),
  `react-native-safe-area-context` (5.8.0 vs 5.9.1), and the
  `@react-native-async-storage/async-storage` pod, `AsyncStorage` (3.0.2 vs
  3.1.1) — all just ordinary version bumps in `package.json` since June that
  never got a matching `pod install`.

**CocoaPods was not runnable in this (Windows) environment** — `pod`,
`gem`, and `ruby` are all unavailable — so this could not be fixed by
literally running `pod install` and committing the regenerated lock.

**Fix applied:** deleted `ios/Podfile.lock` outright rather than
hand-editing it (hand-editing would require exact per-pod SHA1 checksums
that can't be produced without CocoaPods installed, and is exactly the kind
of edit that risks making things worse under time pressure). This repo's
iOS build is a "bare workflow" project (`ios/` committed directly, not
`expo prebuild`-generated) and both `.github/workflows/ios-testflight.yml`
and `ios-debug-build.yml` build via `eas build --platform ios`, which runs
on EAS's macOS cloud infrastructure and performs a real `pod install` as a
standard build phase — confirmed directly by this project's own history, not
just general EAS behavior: `ios/Podfile`'s `post_install` block has a
comment noting "2026-09-01 — this project's first ever [pod install +
Xcode build], via EAS cloud build." Since `ios/` autolinks pods via
`use_native_modules!`/`use_react_native!` (standard RN autolinking, reading
podspecs straight out of `node_modules` — see `ios/Podfile`), a plain
`pod install` reconciles the lock against whatever's actually installed
regardless of what the previous lock said (this is `pod install`'s normal
job, distinct from `pod install --deployment`'s strict check); deleting the
stale lock just means the next build starts that reconciliation from a
clean slate instead of a lock referencing a pod (`NitroAudioRecorderPlayer`)
whose podspec no longer exists anywhere in `node_modules`. `ios/Pods/` itself
is gitignored and was never committed, so there's nothing else stale to
clean up locally.

**Net effect for the next iOS build:** expect a longer-than-usual `pod
install` step on the next EAS cloud build (production or debug profile,
either workflow) since it's resolving every pod fresh rather than from a
matching lock — this is expected and not a sign of a broken build. Nothing
else about the build process changes.

Not run: `eas build` itself (real cloud build cost/quota — left for the
user's next actual build, which is also the first real verification that
`RNAudioRecorderPlayer` links and builds cleanly against the current RN
0.85.3 / New Architecture setup).
