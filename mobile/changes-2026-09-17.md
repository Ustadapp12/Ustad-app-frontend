# Changes 2026-09-17

## Surah search: a searchable list of the whole Quran, reachable from the map

New screen `src/screens/home/SearchSurahsScreen.tsx`, opened by a 🔍 button
added to the map's HUD (beside the XP pill, using the existing `S.hudPill`
style so nothing about the streak/XP pills' own layout moved).

The screen lists all 114 surahs with a search box on top that matches on
English name, Arabic name, or exact surah number. Name matching is
punctuation-insensitive: "al baqarah", "Al-Baqarah" and "albaqarah" all hit,
since both sides are normalised (lowercased, apostrophes/hyphens/spaces
stripped) before comparing. A purely numeric query is treated as an exact
surah-number lookup rather than a substring match, so "2" finds Al-Baqarah
instead of also returning 12, 20-29, 102 and so on.

Tapping a surah that has playable content opens a confirmation card ("Start
Ad-Duha?" with its Arabic name and ayah count); confirming navigates back to
the Map tab with `jumpToSurah` set, and the map scrolls to that surah's first
level. Tapping one that isn't ready yet says so instead of pretending.

A sort control sits beside the search box: a small anchored popover (not a
full dialog) offering **Order** (surah number, the default) and **Size**
(fewest ayahs first). Choosing either applies it and closes immediately;
there's no Cancel button, and tapping outside dismisses.

New supporting files:
- `src/data/allSurahs.ts` — all 114 surahs' number/English name/Arabic
  name/ayah count/revelation place. Surahs 78-114 are reused from the
  already-verified `juz30Surahs.ts` rather than retyped; 1-77 were added and
  cross-checked against api.quran.com's chapter list. Verified independently:
  the catalogue's ayah counts sum to exactly 6236.
- Navigation wiring: `SearchSurahs` added to `RootStackParamList`, `MainTabs`
  retyped as `NavigatorScreenParams<TabParamList>` so a nested
  `navigate('MainTabs', { screen: 'Map', params: {...} })` type-checks, and
  `TabParamList.Map` given an optional `jumpToSurah`.

## The map now lays out the entire Quran (114 surahs), not the 21-surah MVP

`SECTIONS_DEF` was a hand-typed array, one entry per surah, covering 21
surahs. It's now generated from the catalogue, in the same descending order
the map has always used, carried past Juz Amma: 114 down to 1.

Generating it is only possible because of the earlier fixed-road refactor, and
that's worth spelling out, because it looks at first glance like this should
require thousands of hand-tuned numbers. It doesn't. `SectionDef.xFractions`
(the per-node left/right zigzag positions) is dead for rendering — node x
comes from `chapterXFraction(posInChapter)`, which is keyed purely on a node's
slot index within its chapter, so every chapter draws the identical road and a
surah contributes no layout data of its own. `buildLevelsWithReviews()`
already derives a surah's levels from its ayah count. So all a surah actually
needs is its name and ayah count, both of which the catalogue has.
`xFractions` is still populated to satisfy the type; nothing reads it.

Measured result of the expansion (verified with a standalone script
replicating the module's own chunking math against the real catalogue, not
estimated):

- 114 surahs, none missing, 6236 ayahs total
- 4,744 nodes (was ~116)
- 38 seasons (was 7)
- 159 chapters (was 4), max 32 slots in any one chapter

**The invariant that mattered most, checked explicitly:** all 21 previously
live surahs still produce exactly the same level counts as the hand-written
entries did. Their ayah counts in the catalogue match the old hand-typed
values one for one. This is what `trustedLevels`/`SURAH_LEVEL_COUNT` guard —
had any drifted, node-to-lesson mapping would have silently broken for every
existing user. Surah 114 still starts in chapter 0, so a returning user's
starting position is unchanged.

Surah 96 (Al-'Alaq), previously excluded from the curriculum entirely, now
appears in its natural place between 97 and 95. That pushes 95/94/93 down by
its 15 nodes, so those three may land in a different chapter than before.
Harmless: nodes are matched to backend groups by `surahLevelIdx` (the surah's
own internal position), never by chapter or map position.

`utils/mapPhases.ts`: `groupIntoPhases` used a fixed-length `PHASE_SIZES`
array of seven 3s, which silently dumped everything past the 21st surah into
one giant trailing season. Replaced with a constant `PHASE_SIZE = 3` chunked
across the whole list. 21 surahs still yield the same 7 seasons they always
did; 114 yield 38.

The dev-time split-surah tripwire now logs a count instead of listing every
surah. At 21 surahs a chapter-boundary split was a rare event worth naming
(and caused a real production bug once); across the whole Quran every surah
longer than ~60 ayahs spans a 30-node chapter, so naming them individually
would print most of the 114 on every start.

## Seasons no longer gate anything

Sequential season unlocking is gone. Every surah on the map is open from the
start.

The reasoning: the gate stopped being a real barrier the moment search could
jump to any surah on demand, so all it still did was add friction for people
who hadn't found search, while presenting a rule the app itself didn't
enforce. Keeping a lock that one screen can walk straight past is worse than
having no lock.

Removed: `isSeasonUnlocked`, `isSeasonComplete`, `handleUnlockConfirm`,
`handleGatePress`, the `unlockedSeasons` state and its disk read, the
`checkingGate`/`gateTapped` states, and the on-map unlock confirmation card.
`storage.ts`'s `unlockSeason`/`getUnlockedSeasons` are left in place but no
longer called from here.

Deliberately NOT removed: the season signs, their slots in `CHAPTER_SLOTS`, or
the 3-surah season grouping. The signs are now scenery (rendered as a plain
`Image`, not a `TouchableOpacity`), and seasons still earn their keep as the
batch unit for first-level fetches. Keeping their slots means the road's
spacing, `MAP_H`, tile boundaries and chapter rhythm are all untouched by this
change — removing the slots would have shifted every node after each sign.

What still genuinely locks a node:
1. Per-level progress within a surah (the backend's own `locked` status) —
   unchanged.
2. A surah whose content the backend hasn't enabled yet (below).

## Playable-vs-not is now a live backend answer, not a constant in the app

New `src/utils/enabledSurahs.ts` exposes `useEnabledSurahs()`, reading
`learning.mvp_surah_numbers` off the user summary the app already fetches.

This matters because of the backend's own in-progress refactor: its
`get_enabled_surah_numbers()` derives that list live from per-surah content
readiness (text + full-ayah audio + per-word audio) instead of a static env
var. So surahs light up in the app by themselves as their content lands, with
no app release, no constant to bump, and no second place for the two to drift
apart. `MVP_SURAH_NUMBERS` is kept only as the offline/cold-start fallback,
documented as such — it's the set that has been playable since launch, so
falling back to it keeps a freshly opened or offline app showing exactly
today's behaviour rather than briefly drawing every surah as not-ready.

Both the map and the search screen read it:
- `gatedSections` draws every node of a not-yet-enabled surah as `locked`,
  overriding any cached or heuristic status. Drawing it as open would be a
  promise the backend answers with a 404.
- `handleNodePress` intercepts those before the ordinary locked-node shake and
  shows a Lumo message naming the surah, so the tap explains itself instead of
  looking broken.
- `fetchPhase` skips not-yet-enabled surahs entirely. Without this, now that
  most chapters contain some, nearly every chapter change would fire a request
  the backend can only refuse. Its dedup bookkeeping was reordered to run
  *after* that filter, so a phase with nothing fetchable yet stays unmarked and
  retries once its surahs are enabled, rather than being cached as "done".

## Boot and paging cost, given 159 chapters

The mount effect used to walk every unlocked season in the background on a
700ms stagger. That was fine at 7 seasons; at 38 it would mean tens of seconds
of trickling fetches for chapters the user isn't looking at and may never
open. It now warms only the chapters immediately either side of the one being
opened. Anything further is fetched when actually reached — `goToChapter`
fetches what it pages into, the search jump fetches what it lands on, and any
individual node can still resolve itself on tap.

`prefetchAll` in `bootCache.ts` needed no change: it only ever fetched the
first phase (3 surahs) plus the current surah, so it stays bounded regardless
of whether the enabled list holds 21 surahs or 114.

Rendering cost per chapter is unchanged — a chapter is still 30 nodes, and
only one chapter is mounted at a time. `SURAH_LABELS` is computed per chapter
inside `buildMapModel` rather than being a hardcoded per-surah table, so the
new surahs get their labels with no extra work.

The end-of-map "Coming soon!" banner now reads "The whole Quran!" — the final
chapter used to be where the 21-surah curriculum ran out, and is now
Al-Fatihah, the actual end of the road.

## Streak page

- Removed the "SubhanAllah! A full week streak, incredible dedication!" line
  shown at 7+ day streaks; any active streak now shows the same "MashaAllah!
  Keep going" message.
- Removed the swipe-left/right month paging from `StreakCalendar` (the whole
  `PanResponder`). The ‹ › arrow buttons remain the only way to change month.

## Not done / still open

- **Nothing here has been run on a device or emulator.** Type-check passes
  (`tsc --noEmit`, clean) and the jest suite passes (5 suites, 19 tests), and
  the 21-surah level-count invariant was verified by script, but no part of
  this has been seen rendering.
- **The backend's dynamic enabled-list refactor is uncommitted and
  undeployed.** Until it ships, `mvp_surah_numbers` still returns the static
  21 from the env var, so the app will show 21 playable surahs and 93
  not-ready ones. That is the correct behaviour either way; the app needs no
  further change when the backend catches up.
- **Chapter paging is still one chapter at a time via the ‹ › signs.** At 159
  chapters that is not a realistic way to cross the map, which is why search
  exists. Whether the map should stay chapter-paged at all, or become one
  continuous scroll, is still an open design question.
- Per-word audio is the backend's remaining bottleneck for enabling the other
  93 surahs; level skeletons already exist for all 114 there.
