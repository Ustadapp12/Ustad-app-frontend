# Changes 2026-09-04

## Local-notification plumbing (Android permission, channel, icon, library)

**Context:** First real implementation step for on-device notifications (daily practice
reminder, streak-about-to-break, freeze-days-running-out). Not wired into the running app
yet — see below.

**What landed:**
- Installed `@notifee/react-native` (chosen over `expo-notifications`: this is a bare RN
  project with `expo` present only for JS-side tooling — no Expo Modules native runtime is
  integrated into `android/`/`ios/` at all — so `expo-notifications` would need bootstrapping
  a whole new native module system first. Notifee is a standard autolinked RN native module,
  no such bootstrap needed. Notifee is archived by Invertase as of April 2026 but still
  functional; accepted tradeoff for the smaller, lower-risk integration).
- `android/app/src/main/AndroidManifest.xml`: added the `POST_NOTIFICATIONS` permission
  (required on Android 13+/targetSdk 33+ to show any notification, local or pushed). Declaring
  it only makes the runtime prompt requestable — nothing calls it yet.
- `scripts/generate-notification-icon.mjs` (new) + `npm run generate:icons:notification`:
  generates `ic_notification.png` at all 5 density buckets (`drawable-mdpi` through
  `-xxxhdpi`) from `assets/images/lumo_transparent.png`, rebuilt as solid white with the
  source's original alpha mask — Android discards a notification icon's RGB and masks it to
  a flat colour, so the regular multi-colour mascot would render as a grey blob. Chained into
  `npm run build:apk` / `build:aab` alongside the existing `generate:icons` step so it's not
  forgotten on a real build.
- `src/services/localNotifications.ts` (new): the notification channel (`reminders`,
  created idempotently via notifee's JS API — no native Kotlin needed for this, unlike a
  bare-FCM setup), the 3 pure trigger-time computation functions (daily reminder,
  streak-about-to-break, freeze-days-running-out — verified against real backend fields:
  `current_streak`/`streak_state`/`freeze_days_remaining` from `/complete`), and a
  notifee-backed `refreshLocalNotifications()` orchestrator. Follows the existing
  `analytics.ts`/`googleAuth.ts` lazy-require discipline — no other file imports notifee
  directly, native-module absence degrades to a no-op instead of throwing.

**Update, same day — wired in for real:**
- `authStore.ts`'s `applyFreshLearning()` (runs on every fresh learning payload: login,
  register, hydrate, refresh) now calls `refreshLocalNotifications()` with the real
  `current_streak`/`streak_state`/`freeze_days_remaining`, fire-and-forget, try/caught.
- `lessonStore.ts`'s `completeSession()` now stamps today as practised (new
  `getLastActiveLocalDate`/`setLastActiveLocalDate` in `utils/storage.ts`, since the backend
  doesn't return this — the client is the only side that knows the instant `/complete`
  succeeds), calls `refreshLocalNotifications()` with the freshly-completed streak state, and
  — exactly once, ever, gated by a new `wasLocalNotifPermissionAsked` flag — calls
  `requestLocalNotificationPermission()` the first time any lesson is completed.
- Net effect: **streak-about-to-break and freeze-days-running-out are now fully live**,
  contingent only on an actual native build (see below) — no further wiring needed for
  either.

**Still not done, and this is the one real gap left:**
- **Daily practice reminder has no reminder hour to schedule against.** Every call site
  above passes `reminderHour: null` on purpose — there's no onboarding picker, and the
  backend's `language_prefs` serialization is an explicit allowlist (`avatar_variant`, etc.),
  so exposing a new `reminderHour` field also needs a small backend schema addition, not
  just a client picker. This is the one piece that isn't a "wire it up" task.
- "Hearts are full again" stays excluded — same hearts-UI gap as before.
