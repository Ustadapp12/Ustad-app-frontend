# Changes 2026-09-11

## Fixed the real cause of eas submit hanging 55-66 minutes then failing on TestFlight

**Bug:** every production iOS build (2x on 2026-09-10) built fine in under 6
minutes, then the "Submit latest build to TestFlight" step sat for 55-66 minutes
before failing with a content-free "Something went wrong when submitting your app
to Apple App Store Connect."

**Root cause:** this is a bare-workflow iOS project (`ios/` is committed, not
generated by `expo prebuild`) — `app.json`'s `ios.buildNumber` is never read at
build time. The real source is `ios/UstadApp.xcodeproj/project.pbxproj`'s
`CURRENT_PROJECT_VERSION`, frozen at `100` in git. `eas.json`'s production
profile had `autoIncrement: true`, which does naive local math off that frozen
value with no awareness of what's actually registered on App Store Connect.

This exact setup already caused this exact symptom once before — "hanging eas
submit for 40+ minutes" — diagnosed and fixed on 2026-09-03 (commits `0815f8e`,
`601d406`), but **only for `ios-debug-build.yml`**. That fix (stop relying on
autoIncrement; stamp a deterministic, always-increasing build number directly
into `project.pbxproj` in CI) was never ported to `ios-testflight.yml`, the
production workflow — which kept running on the same `autoIncrement: true`
config already known to be unreliable.

Both of 2026-09-10's builds independently computed build 356 via autoIncrement
(landing on the same number twice, since neither ever got confirmed-accepted by
Apple). Build 355 was the last one Apple actually accepted (2026-09-07). Very
likely: 356 was still stuck mid-processing on Apple's side from the first
attempt when the second attempt tried to upload another binary under the same
build number, and Apple's backend doesn't handle that gracefully — matching the
prior incident's diagnosis precisely.

**Fix:**
- `.github/workflows/ios-testflight.yml` — added a "Stamp a collision-proof
  build number" step (mirrors `ios-debug-build.yml`'s own step) right before
  the build step: patches `project.pbxproj`'s `CURRENT_PROJECT_VERSION` to
  `10000 + github.run_number` — deterministic, always increasing, refuses to
  build at all if the regex doesn't match (no silent stale-number builds).
  Baseline 10000 is deliberately far above both the stuck 356 and
  `ios-debug-build.yml`'s own `100 + run_number` range, since debug and
  production builds share one build-number namespace on the same TestFlight
  app.
- `mobile/eas.json` — removed `"autoIncrement": true` from the production
  build profile, same as was already done for development on 2026-09-03.
