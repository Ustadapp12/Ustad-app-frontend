# Changes 2026-09-20

Live iOS TestFlight testing session on build 10037 (the whole-Quran expansion
build from 2026-09-18). Everything below was found and fixed across that
testing pass; none of it had shipped in any build before this one.

## Fixed: map jump-to-recommended landed somewhere different almost every time

Two distinct bugs stacked on top of each other, both in `MapScreen.tsx`.

**Bug 1 — spurious re-firing.** `jumpToRecommended` is a `useCallback` whose
identity churns on nearly every render (it depends on `firstActiveNode`,
which is a fresh object every render since `enrichedSections`/
`allEnrichedNodes` are never memoized). Two effects — the `tabPress`
listener and the "re-scroll after returning from a lesson" effect — listed
`jumpToRecommended` itself as a dependency, so they were re-running on
*every* render rather than only on their real trigger. Each spurious re-run
called `jumpToRecommended()`, whose first line unconditionally clears
`manualChapterRef.current` (the "user paged here by hand, leave them alone"
flag) and can snap the viewport back to the recommended node. Reported as
"touching any node/chapter arrow takes me back to Continue here."

Fixed with a stable `jumpToRecommendedRef`, updated by its own effect;
the `tabPress` and `returnedFromLevelTick` effects now depend only on their
real trigger and call through the ref.

**Bug 2 — wrong destination even on a legitimate jump.** Once bug 1 was
fixed, a second bug surfaced: pressing the Home tab on purpose still landed
in a different place almost every time. `chapterForRecommended` fell back
to `SURAH_TO_CHAPTER[surah]` (the surah's *opening* chapter) whenever
`fullLevels[recommendedSurah]` hadn't loaded yet — frequently the wrong
chapter now that most surahs span several chapters post-expansion. The jump
fired immediately against that guess, resolved to a placeholder first-level
node, and discarded the real answer the moment it later arrived. Whether a
given tap landed correctly was pure timing luck.

Fixed: `jumpToRecommended` now refuses to jump at all until
`fullLevels[recommendedSurah]` is actually trustworthy — it defers via
`pendingRecommendedJumpRef` instead of guessing, and a new effect replays
the deferred jump automatically once that surah's real data lands. Manual
navigation (chapter arrows, search-jump) clears the pending flag so it can
never override something the user did by hand while it was waiting.

## Fixed: "Hear and fill" always felt slow on the first option tapped

`AudioFill`'s preload effect queued `segment_audio_urls` ahead of
`ex.options` in the array handed to `preloadAudioUrls` (which loads 4 at a
time, in order). Option 1 is the one people almost always tap first, so it
was the one most likely to still be mid-preload — falling through to a cold
on-demand load (a real network fetch) instead of playing an already-warm
clip. Reordered so options are queued first.

## Diagnostics added: "Couldn't open {surah}" from search

Root cause not yet confirmed — every backend path this could hit (content
status, per-surah levels, the batched first-levels endpoint, session start)
tested healthy in isolation. Added `captureError` calls at both places
`handleNodePress` can produce this message (the on-demand first-level fetch
returning empty/throwing, and the `!node.resolved` branch's `trustedLevels`
rejection), tagged with the surah number and which path fired, so the next
real repro reports the actual cause instead of needing another guess.

Also found in passing, backend-side (`app/content/repository.py`):
`bust_enabled_surahs_cache()` exists but is never called anywhere — nothing
invalidates the Redis-cached enabled-surahs list when a surah's content
flags flip, it only self-heals on a 60s TTL. Not applied (backend repo is
read-only from this session) — patch handed to the user for
`scripts/enable_surah.py`.

## Added: search results show open/done status; locked map nodes offer to jump to their surah

`SearchSurahsScreen` now fetches every surah's first-level status in one
batched call and colors each row gold (open: available/in-progress) or
green (done: completed), with a small legend under the search bar.

Tapping a **locked** node on the map itself no longer just shakes and stops
— it now also offers "Start {surah}?", identical to picking that surah from
search. Built by extracting the shared pieces so both entry points are
actually the same code, not a duplicate: `StartSurahModal` (new component)
replaces the confirm dialog that used to be inline in
`SearchSurahsScreen`, and `jumpToSurahStart()` (extracted from the old
search-jump effect) is now called by both the search-jump route-param
effect and the new locked-node confirm.

## Session 2: build 10038 findings, chapter-cut restructure, more UI fixes

Build 10038 (see versions.md) shipped everything above. Testing it live
surfaced more, all in `MapScreen.tsx` unless noted.

**Locked-node "Start Surah?" scoped down.** It was firing on every locked
node, not just a surah's own opening one — confusing on an ordinary
sequential lock (finish the previous level first) where the offer to jump
to the surah's start is irrelevant noise. Now gated on
`node.surahLevelIdx === 0`; every other locked node just shakes.

**Chapter-cut algorithm restructured** to fix a real (if narrow) case: a
surah continuing into a new chapter could have that chapter open on a
REVIEW node (e.g. surah 39/Az-Zumar's chapter 55 opened on `39_review_10`,
ayahs 37-40, with none of its own normal levels in view first — confirmed
not a data bug, a coincidence of that surah's cumulative offset landing the
30-node cut exactly there). Verified systemic: the same script that found
this found **53 such violations across the 114 surahs under the old
algorithm** — every surah past ~90 ayahs was affected somewhere, not just
39. Fixed by deferring the cut one level whenever it would land on a
continuing review (kept on the closing chapter as an extra slot instead —
guaranteed the next level is normal, since reviews never run back-to-back).
`chapterForLevel` is no longer a formula (`Math.floor` division assumed
every chapter was exactly 30 levels, which is no longer true) — it's now a
direct table built off the same construction pass, so forward/reverse
mapping can't disagree by construction. Verified against all 114 surahs:
0 violations after, chapter count 159→158, 4,744 total levels unchanged
(conservation check), 30 of 114 surahs' opening chapters shifted as a
result (harmless — chapter index is never persisted, always recomputed
live, and no UI displays a literal chapter number).

**Other fixes/changes, per explicit request:**
- Surah name label was appearing on every chapter a surah spans, not just
  its true opening one (same root cause class as the chapter-cut bug: a
  surah gets a `section` entry per chapter it touches). Now gated on
  `surahLevelIdx === 0` the same way.
- `suppressFollowRef` wasn't being reset on two failure paths in
  `handleNodePress` (the completed-node re-verify and the unresolved-node
  resolve, both when the fetch succeeded but returned no matching group) —
  left the viewport's auto-follow silently skipped on the next legitimate
  change, which is what "landed somewhere different than before" traced to
  after a failed open. Both now reset the flag.
- Start-prompt card's time estimate ("4-5 min"/"6-8 min") replaced with
  "Starting now"/"Starting review now"/"Starting again" — the card's own
  title already names the surah, so this isn't repeated.
- Search screen: added a third sort option, "Status" — open
  (available/in-progress) first, locked/unopened in the middle, completed
  last, surah-number order within each group. Default sort unchanged.
- Map search button: 32px → 96px (3x), per request.
- Streak page: removed the translucent gray glow ellipse behind the streak
  number entirely; flame animation 132px → 160px with a -20px shift up
  (was sitting low against the number/label stack).

**Backend finding, not a code bug:** `list_lesson_groups`'s Redis cache
(1-hour TTL, same missing-invalidation pattern as the enabled-surahs cache
found earlier) was found actively serving stale EMPTY results for most
surahs — confirmed live: surahs 2, 6, 39, 42, 55, 68 all returned `[]` from
`/learning/surahs/{n}/levels` despite verified-correct underlying data
(e.g. surah 39 has 57 real docs in Mongo). Surahs 100/114 (the original
short set) were unaffected. This is very likely the actual cause behind
ongoing "couldn't open {surah}" reports, independent of the diagnostic
captureError calls added earlier today. Not fixed from this session (would
require a live Redis mutation, held for explicit user go-ahead per the
backend's read-only rule) — flagged to the user, awaiting decision.

Verification this round: `tsc --noEmit` clean after every change (re-run
personally after each agent handback, not just trusted). Still nothing run
on a real device — build 10038 was the first time any of session 1's
changes were actually opened by a user, and it immediately surfaced three
