# Changes 2026-09-22

## Fixed: offline launch was logging in sessions out

**Report:** "left and came back offline, was logged out even though net came
back."

**Root cause (`src/store/authStore.ts`, `hydrateInner`):** every cold start
with a stored session calls `authApi.me()` to re-verify it. The result was
consumed as `authApi.me().catch(() => null)` — collapsing every possible
failure (a real "this session is invalid" 401, *and* "the request never
reached the server at all") into the same `null`. Either one then wiped the
stored tokens and set `user: null`, signing the person out. A pure
connectivity failure (no signal, DNS/TLS blip, the client's own 30s timeout —
`ApiError` status `0`, see `src/api/client.ts`) was being treated exactly
like the server explicitly rejecting the session, even though nothing was
ever actually asked. Once logged out this way there was nothing left to
re-hydrate from, so the session stayed lost even after the network came back.

**Fix:** `hydrateInner` now inspects the caught error. Tokens/user are only
cleared for a genuine `ApiError` with `status === 401` (api/client.ts already
tries one silent refresh internally before ever surfacing a 401, so this
means the refresh token itself was rejected — a real "log out"). Any other
failure (status `0`, timeout, anything else) falls back to the locally
cached user (`getStoredUser()`) and keeps the tokens, so the session survives
being opened offline. `refreshLearning`'s periodic poll got the same
401-vs-everything-else check.

## Fixed (2nd pass, same report): `api/client.ts` was mislabeling a network failure DURING token refresh as a real logout

User re-tested and still got logged out even with the fix above in place (in
source — see "not yet built" note at the bottom; the report that prompted
this second pass was almost certainly still against the old, unfixed build).
While auditing every path that can clear a session, found a second, distinct
bug in `refreshAccess()` (`src/api/client.ts`) that the first fix didn't
cover, and that would independently log someone out even with it applied:

Any authenticated request that gets a 401 (normal once the access token
expires, e.g. after the app sits backgrounded) triggers `refreshAccess()`,
which POSTs to `/auth/refresh`. That fetch had **no try/catch** around it. If
it failed for a network reason (not the server rejecting the refresh token,
just "couldn't reach it" — exactly the kind of flaky signal you'd get right
as connectivity comes back) it never reached the `if (!res.ok)` check at
all, so it threw a bare JS error. That error was caught one level up in
`api()`'s 401-retry block and turned into `new ApiError('Unauthorized', 401,
null)` unconditionally — mislabeling a pure connectivity failure as a real
"session rejected" response. That fake 401 is indistinguishable from a real
one to every caller, including `hydrateInner`'s `isRealAuthRejection` check
added in the first fix above — so it would still log the user out, just from
a narrower trigger (a 401 mid-refresh during a flaky reconnect, rather than
being offline from the very start of the request).

**Fix:** `refreshAccess()`'s fetch is now wrapped in its own try/catch and
throws `ApiError` status `0` (not `401`) when it can't reach the server at
all, same convention as everywhere else in this file. `api()`'s 401-retry
catch block now rethrows an `ApiError` as-is instead of collapsing every
failure into a blanket 401, so a network failure during refresh finally
propagates as what it actually is.

## Fixed: local notifications silently skipped a refresh when offline

Confirmed with the user this was also part of the offline report ("allow
the notifications to show idle whenever" → "offline too, send them").
`services/localNotifications.ts` is documented as needing no backend/network
at all, but `refreshLocalNotifications()` was only ever called with a
`StreakState` built from a **fresh** `learningApi.me()` response
(`authStore.applyFreshLearning`) — so an offline hydrate, which never gets a
fresh `learning` payload, silently skipped rescheduling entirely, leaving
streak/freeze reminders stale.

Added a small persisted snapshot (`current_streak`/`streak_state`/
`freeze_days_remaining` only — `utils/storage.ts`'s
`getStoredStreakSnapshot`/`setStoredStreakSnapshot`), written every time
`applyFreshLearning` gets a real response. `hydrateInner`'s offline fallback
(above) now reads that snapshot back and still calls
`refreshLocalNotifications()` with it, so an offline launch keeps reminders
on track from the last known state instead of freezing them until the next
successful network call.

## Added: offline banner, shown regardless of login state

New `isOffline` flag on `authStore`, and a small `OfflineBanner` component
mounted once in `RootNavigator` (above the stack, so it shows on every
screen). Two sources feed it:

- `SplashScreen`'s existing `healthCheck()` call (fires on every launch, with
  or without a stored session) now also sets `isOffline` — this is what
  covers a signed-out or never-onboarded device, which `hydrate()` never
  touches at all when there's no token to check.
- `hydrateInner` and `refreshLearning` set it from their own network-vs-401
  distinction above, so it also reflects reality for an already-signed-in
  session, both at launch and while the app is running.

Purely informational — nothing else in the app gates on it.

## Map (`MapScreen.tsx`): search button size, and the mountain-clip bug it was already causing

- Search button (below the streak pill) bumped from 2x (64px) to 3x (96px)
  original size, per request. Added `alignSelf: 'flex-start'` so it hugs its
  own width instead of stretching to match its column's width, keeping its
  left edge flush with the streak pill above it.
- **Found while investigating a report that the mountain skyline art was
  getting cut off:** the mountain `<Image>` was sized
  `height: SKY_BOUNDARY_Y + 28 - hudHeight` — shrinking every time the HUD
  got taller (e.g. from the search button above). With `resizeMode="cover"`,
  a shorter box doesn't just show less mountain, it can flip which axis gets
  cropped: once the box got wide enough relative to its shrunken height,
  `cover` switched from trimming the image's sides to trimming its top,
  chopping the peaks off — and this would have gotten worse the moment the
  search button grew. Fixed by always giving the `Image` its full,
  hudHeight-independent height (so `cover`'s crop math never changes) and
  clipping the hudHeight-tall slice that belongs behind the HUD with a
  wrapping `overflow: 'hidden'` View instead. Same visible "starts below the
  HUD" result, but the image itself is never asked to squeeze into a shorter
  box.
