# Changes 2026-09-10

## Every pure-white color swapped to #F5F7FA

User request: every screen color that was pure white, everywhere. Found and
replaced every exact occurrence of `'white'`, `'#fff'`/`'#FFF'`, and
`'#ffffff'`/`'#FFFFFF'` as a color value across `src/` (89 replacements, 25
files) with `#F5F7FA` — which wasn't a new color invented for this, it's the
same off-white already used for the map's level-action-card popouts
(`colors.levelCardOffWhite`). Includes `theme/colors.ts`'s `white` and
(unused) `cardBg` constants, so anything that already went through
`colors.white` picks it up automatically alongside the ~25 files with
hardcoded literals.

Deliberately left untouched: `rgba(255,255,255,0.X)` translucent overlays
(frosted-glass panel backgrounds, text-shadow highlights, subtle glass
borders across `MapScreen`/`HelpScreen`/`DailyQuestScreen`/etc.) — those are
semi-transparent design accents layered over other content, not opaque
"screen color," so a literal reading of "pure white" doesn't reach them.
`npx tsc --noEmit` clean.

## Wired up inactivity_nudge and streak_lost local notifications

`services/localNotifications.ts` had 4 of 7 `LocalNotificationKind`s with real
range/time logic; `inactivity_nudge`, `milestone_completed`, and `streak_lost` had
message text but no scheduling logic, per the user's spec:

- `computeInactivityNudge(now)` — no condition, always (re)schedules itself for
  `now + 24h`. Every call to `refreshLocalNotifications()` (hydrate/login/lesson-
  complete) IS an "app was just opened" event, so this always pushes the fire time
  forward another 24h on a real open; it only actually fires if that never
  happens, via the same replace-by-id `createTriggerNotification` semantics
  everything else here already relies on.
- `computeStreakLost(streak, now)` — streak loss has no backend event (see
  `applyFreshLearning`'s own comment in `authStore.ts`) and is only ever
  discovered client-side, after the fact, the next time the app opens — too late
  for a push, since by then the user's already looking at `StreakLostModal`. So
  instead of reacting to a loss already having happened, this predicts the exact
  day the current freeze window runs out (`today + freezeDaysRemaining`, same
  count `freeze_days_running_out` already tracks) and schedules for that day —
  arriving right as the streak actually breaks. Cancels itself the same way
  `freeze_days_running_out` does if the user repairs the streak first.
- `milestone_completed` NOT wired — it's event-triggered (surah completion), not
  a range/time schedule, and needs per-surah level-completion data that lives in
  `MapScreen.tsx`'s `fullLevels`, not in `StreakState`. Recommended approach (not
  yet built, needs confirmation): fire the first time a surah's last level flips
  to `'completed'` — `MapScreen.tsx` already has this exact check pattern
  (`isSeasonComplete()`, ~line 2404, checks the last level of the last surah in a
  season) — scoped to one surah instead of a season, gated by a persisted
  "already notified for this surah" set so it only fires once each, and scheduled
  a few hours out rather than immediately (the user is already looking at the
  screen at the moment it happens).

Both new kinds added to the `refreshLocalNotifications()` computed list and to
the `REAL_NOTIFICATIONS_DISABLED` cleanup list. **`REAL_NOTIFICATIONS_DISABLED`
is still `true`** (left as-is — flipping it live-enables all 6 wired kinds at
once, a separate decision from just adding the compute logic). `npx tsc --noEmit`
clean.

## Arabic fonts not changing / falling back to default on iOS

**Platform:** iOS only (Android's filename-based font lookup tolerated this; iOS does not).

**Bug:** Usmani and Indo-Pak sometimes rendered as the exact same (system default)
font on iOS, and sometimes the chosen script didn't visibly change anything at all.

**Root cause:** every `fontFamily` string in the app (`NotoNaskhArabic_400Regular`,
`NotoNastaliqUrdu`, and `AmiriRegular` in `utils/arabicFont.ts`'s `scriptToFontFamily`)
was a leftover from an earlier expo-font-based setup. The app no longer loads fonts
that way — `scripts/link-fonts.mjs` bundles the raw `.ttf` files and registers them
natively via `UIAppFonts` in Info.plist / `assets/fonts` on Android — and on iOS,
`fontFamily` is resolved against the font's own embedded PostScript name (via
`UIFont`), not the filename or any string the JS side happens to use. Inspected the
actual shipped `.ttf` files' name tables directly:

| Script                | JS string was            | Font's real PostScript name |
|------------------------|---------------------------|------------------------------|
| Usmani (default/Naskh) | `NotoNaskhArabic_400Regular` | `NotoNaskhArabic-Regular` |
| Indo-Pak (Nastaliq)    | `NotoNastaliqUrdu`        | `NotoNastaliqUrdu-Regular` |
| Amiri                  | `AmiriRegular`             | `Amiri-Regular` |

None of the three matched, so iOS silently fell back to the system font for all of
them — which is also why Usmani and Indo-Pak looked identical: both failed to
resolve and landed on the same system fallback. Android's asset-based font lookup
is more forgiving in some builds, which is why this read as iOS-only.

**Fix:** updated every hardcoded `fontFamily` literal to the real PostScript name —
`utils/arabicFont.ts`, `theme/typography.ts`, `screens/profile/ProfileScreen.tsx`,
`screens/onboarding/OnboardScriptScreen.tsx`, `screens/startup/SplashScreen.tsx`,
`screens/lesson/LessonSessionScreen.tsx` (16 style declarations). `npx tsc --noEmit`
clean.

**Also fixed, same class of bug: Nunito (English/Latin UI text).**
`ios/UstadApp/Fonts/Nunito-Regular.ttf` and `Nunito-Bold.ttf` were themselves
mislabeled internally — embedded Family `Nunito ExtraLight` (subfamily
`Regular`/`Bold`), PostScript `NunitoExtraLight-Regular`/`-Bold`, not `Nunito`/
`Nunito-Regular`/`Nunito-Bold`. Confirmed this is an upstream bug in
`cdn.jsdelivr.net/fontsource/fonts/nunito@5.2.5` itself (re-fetched the exact URL
`link-fonts.mjs` used — same wrong name table came back), not a one-off bad
download, so re-running the existing script would not have fixed it. Every
`fontFamily: 'Nunito_400Regular'`/`'Nunito_700Bold'` literal in the app (48 files)
inherited the same "string doesn't match the font's real name" failure as the
Arabic fonts above, on top of the fact that even a matching name would have
rendered in the wrong (extra-light) weight, since the files themselves are the
wrong weight.

Fix: pulled the real Nunito 400/700 statics directly from Google's own
fonts.gstatic.com (the `css2` API only serves `.woff`/`.woff2` by content
negotiation; fetched with an old-browser User-Agent to get `.woff`, then unwrapped
the WOFF container back to a raw `.ttf` — it's just zlib-compressed sfnt tables
behind a small header per the WOFF spec, no external converter needed). Verified
the result: valid sfnt (16 tables incl. `glyf`/`loca`/`cmap`/`hmtx`/`OS/2`),
correct name table (`Nunito` / `Regular` or `Bold` / `Nunito-Regular` or
`Nunito-Bold`). Replaced the `.ttf` in all three shipped locations
(`assets/fonts/`, `android/app/src/main/assets/fonts/`, `ios/UstadApp/Fonts/`),
bulk-renamed every `Nunito_400Regular`→`Nunito-Regular` and
`Nunito_700Bold`→`Nunito-Bold` literal across `src/` (48 files), and removed
Nunito from `link-fonts.mjs`'s `DOWNLOADS` map with a comment explaining why, so a
future fresh checkout can't silently re-pull the broken Fontsource file. `npx tsc
--noEmit` clean. No Info.plist/pbxproj/gradle changes needed — filenames didn't
change, only the bytes and the JS-side family strings.

## Level closes after backgrounding the app mid-lesson

**Platform:** iOS and Android both (same JS logic), reported on iOS.

**Bug (long-standing, previously reported):** switch to another app mid-level, come
back, answer one more exercise, and the level immediately ends/closes.

**Root cause:** `App.tsx` had a 60-second "grace timer" that, on any backgrounding
that lasted more than a minute, silently called `abandonActiveLessonSessionSilent()`
— marking the session abandoned server-side — with **no client-side awareness**.
`LessonSessionScreen` stayed mounted showing the same exercise as before, oblivious.
The next answer (`submitAnswer` → `formulaAttempt`) hit the now-gone session and got
back a 404, which its own catch branch (existing code, `LessonSessionScreen.tsx`
~line 3069) treats as "level over" and force-navigates to `LessonComplete` with
`xp: 0, scorePct: 0, stars: 1` — discarding whatever real progress had been made.
That's the "level closes" the user's been describing.

This directly undid the 2026-09-06 session-resume fix (`7640a5b`): that fix made
`startSession()` reconnect to an in-progress session instead of always abandoning
it, specifically so an interruption wouldn't lose progress — but the 60s timer kept
proactively abandoning sessions *before* the user ever got a chance to trigger that
resume path, since the screen never remounts (and so never calls `startSession()`
again) on a mere background/foreground cycle where the JS engine stays alive.
Confirmed the backend's own staleness backstop
(`expire_stale_active_sessions`, `lesson_session_stale_minutes = 120`) already
handles genuinely-abandoned sessions on a 2-hour timeout, making the aggressive
60-second client-side timer both redundant and actively harmful.

**Fix:** removed the grace-timer/`abandonActiveLessonSessionSilent()` call from
`App.tsx`'s AppState listener entirely. Backgrounding no longer proactively ends a
lesson session — a real return from background now just resumes normally through
the existing (already-shipped) resume mechanism, no matter how long the user was
away, up to the backend's 2-hour staleness window. `endUsageSession()` /
`syncDeviceTimezone()` / `refreshLearning()` on return are unchanged. `npx tsc
--noEmit` clean.

**Also noted, not touched:** `src/hooks/useAbandonLessonOnBackground.ts` is dead
code — defined but never imported/called anywhere in the app. It duplicates (and
philosophically contradicts) the logic just removed from `App.tsx`. Left in place
since deleting unused files wasn't asked for, but worth removing later so nobody
wires it back in and reintroduces this exact bug.

**Not yet verified by hand on a device** — background the app mid-level for 2+
minutes, return, and confirm the same exercise/progress is still there and a
submitted answer succeeds normally.

## White screen mid-exercise, iOS only

**Platform:** iOS only — same JS/animation code runs on Android; only the visible
symptom is platform-specific (see root cause).

**Bug:** screenshot showed `LessonHeader` (X button, progress bar, hearts, Hint
chip) rendering completely normally, with the exercise content beneath it totally
blank/white, before it "loads again" a moment later. Reported as present since iOS
existed for this app, never on Android.

**Root cause:** `LessonSessionScreen.tsx`'s `ExerciseSlide` wrapper (~line 2647)
remounts fresh on every exercise change (`key={exercise.ex_id}` on its parent) to
slide each new exercise in from the right. It started its `translateX` Animated
value at the full screen `width` — i.e. the new exercise's content was mounted
completely off-screen — and only kicked the slide-in animation off inside a
`useEffect`, which React/RN runs strictly *after* the first frame is already
committed and painted. That guarantees at least one fully-off-screen frame on
every single exercise transition. `LessonHeader` is a sibling rendered outside
`ExerciseSlide`, so it kept showing fine while the entire exercise body beneath it
was blank. Android's compositor apparently holds the previous frame through that
same gap (matches the exact wording of an earlier, different white-screen fix's
comment in this codebase — Android masking a real underlying gap that iOS
doesn't), which is why this only ever showed up on iOS despite being the same JS
logic on both platforms.

**Fix:** two changes to `ExerciseSlide`, together:
- `useLayoutEffect` instead of `useEffect`, so the native `.start()` command is
  queued in the same commit as the view's mount — before that first frame is
  handed to the native side to paint — instead of one JS-thread round-trip later.
- Starting offset reduced from a full screen `width` to a fixed 40px (and duration
  260ms → 220ms to match). Even if the animation start is ever still delayed by a
  frame or two, the exercise content now sits almost exactly in place instead of
  fully off-screen — worst case a barely-noticeable shift, never a blank screen.

Removed the now-unused `useWindowDimensions` import. `npx tsc --noEmit` clean.
**Not yet verified by hand on a device** — would need to watch several
exercise-to-exercise transitions on a real iPhone to confirm the blank frame is
actually gone (a code-level timing fix like this can't be fully proven from static
analysis alone).
