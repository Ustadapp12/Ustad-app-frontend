# Changes 2026-09-16

## Fixed the Play Console "16 KB page size" crash warning: NDK 27 -> 28

`android/build.gradle`'s `ndkVersion` was `27.1.12297006`; Google's Play
Console flagged this with "your app could crash on 16 KB devices" — NDK r27
has a documented ELF-alignment bug in its 16 KB page-size support, fixed in
r28. Bumped to `28.0.13004108`.

This project's build pipeline forces its own NDK version regardless of what
`android/build.gradle` says — `C:\gradle-local-cache\init.d\redirect-builds.gradle`
overrides `ndkVersion` to work around an unrelated NDK-27 linker bug
(`ld.lld: undefined symbol: __cxa_guard_acquire`) via a `-lc++_shared` cmake
flag. Updated that init script's forced version to `28.0.13004108` too, or
the `android/build.gradle` edit alone would have been silently overridden on
every real build. Validated with a throwaway smoke build (versionCode
26091601, versionName "1.0.99-ndktest", not logged in versions.md, never
distributed) — all three ABIs (arm64-v8a, armeabi-v7a, x86_64) compiled clean
with NDK 28, no linker errors, confirming the old `-lc++_shared` workaround
still holds on the new NDK.

## Enabled R8 (code shrinking) for the first time on this codebase

`android/app/build.gradle`: `enableProguardInReleaseBuilds` was hardcoded
`false` since the project's first release — this is why Play Console kept
showing a "Low" App Optimization score (0% shrinking, 24.4 MB uncompressed
DEX) on every build. Flipped to `true`, added `shrinkResources
enableProguardInReleaseBuilds` (resource shrinking was never on either — no
`shrinkResources` line existed at all before this).

Added two keep-rule blocks to `android/app/proguard-rules.pro` (previously
just the empty RN template) for the two areas judged highest-risk for
release-only R8 breakage: Google Sign-In (`com.google.android.gms.auth.api.signin.**`,
`com.google.android.gms.common.api.**`) and Firebase (`com.google.firebase.**`).
`@notifee/react-native` and `react-native-svg` already ship their own
consumer proguard rules bundled in their AAR (found in node_modules), so
nothing added for those.

Verified via the actual R8 output, not just "BUILD SUCCESSFUL":
- `outputs/mapping/release/usage.txt` (R8's list of every class it removed)
  shows **zero** Google Sign-In or Firebase classes stripped — the keep
  rules held.
- This app's own native code (`UstadNavigationBarModule`, `MainActivity`,
  etc.) — only auto-generated `BuildConfig`/`R$*` classes were removed,
  normal R8 behavior, nothing load-bearing touched.
- `react-native-sound` (recitation audio playback) — only `BuildConfig`/`R`
  and two unused Kotlin lambda-continuation classes removed; the core
  `Sound` class survived.
- `react-native-keychain` (token storage) — a larger set of classes removed,
  but they're the alternate cipher-storage backends
  (`CipherStorageKeystoreRsaEcb`, the biometric result handlers) that this
  app's `minSdkVersion 24` shouldn't need anyway; plausible legitimate
  dead-code elimination, not confirmed safe by static analysis alone.
- Combined `classes.dex` + `classes2.dex`: **7.9 MB**, down from the 24.4 MB
  uncompressed baseline Play Console reported before this change — a ~68%
  reduction, more than the typically-quoted 30-40% for an RN app.

Real device regression (Google Sign-In specifically, plus login persistence
and audio playback) is still the user's to run before Play Store submission
— static R8 output analysis is a strong signal, not a substitute for it. R8
also printed several `Invalid stack map table` warnings against Google's own
`play-services-auth-21.5.0-runtime.jar` during the build — these are a known
R8 quirk with Google's pre-obfuscated Play Services AARs and did not fail
the build, but they're exactly why Google Sign-In is the top thing to
manually verify.

## Discovered `android/` had drifted from source — fixed mid-session

While syncing this session's edits to `C:\BuildProjects\ustadapp-mobile\`
(native `android/` files aren't covered by the routine src/assets robocopy
sync — a known gap, see `reference_apk_build.md`), a full diff turned up
that the build tree's `AndroidManifest.xml` was missing the
`POST_NOTIFICATIONS` permission and the touchscreen/microphone
`<uses-feature>` distribution filters entirely, and the `ic_notification.png`
drawables were missing from every density folder. All of these existed in
the OneDrive source (added in an earlier, unrelated session) but had never
once made it into an actual build. Without `POST_NOTIFICATIONS`, no
notification — local or otherwise — can prompt for permission on Android
13+, regardless of anything on the JS side. Synced `res/`, `assets/fonts/`,
and `AndroidManifest.xml` in full (excluding `splash_logo.png`, which
BuildProjects intentionally keeps newer/smaller than source per a prior
session's note).

Not fixed: the `ic_notification.png` assets are still unreferenced by any
`smallIcon` field in `localNotifications.ts` or an AndroidManifest
meta-data default, so notifications will render using the app's full-color
launcher icon rather than the dedicated white-silhouette icon someone
already prepared. Cosmetic, not functional — left alone, not in scope for
this session's ask.

## Streak page redesign: Duolingo-style practice calendar

Requested redesign of `StreakScreen.tsx`, based on a Duolingo screenshot sent
as style inspiration (flame-above-date grid, not the PERSONAL/FRIENDS tabs or
"Streak Society" section — scoped down to the calendar visual only per
discussion).

Before writing any calendar code, checked whether the backend actually has
day-by-day streak history to render truthfully — it doesn't. `Streak` (see
`ustadAppBackend/app/models_pg/streaks.py`) only stores the live aggregate
(`current_streak`, `last_active_at`); there's no log of which past dates were
practiced vs. freeze-covered (this is the same gap `utils/streak.ts`'s
`checkStreakLoss` comment already documents on the frontend side). Rather
than fabricate flames on unverified past dates, asked the user how to source
this and they picked the middle option: a new real, read-only backend
endpoint for practiced days only, freeze days left undistinguished for now.

**Backend** (`ustadAppBackend/app/learning/`, edited but NOT committed/pushed
— per usual, that's the user's to review and deploy):
- `schemas.py`: added `StreakCalendarOut { start_date, practiced_dates }`.
- `service.py`: added `get_streak_calendar()` — `practiced_dates` is the
  distinct local (`_resolve_tz`) calendar dates with a `LessonSession` row
  where `ended_at IS NOT NULL`. This mirrors what actually advances a streak
  server-side (`complete_session`'s `real_completion` gate fires on *any*
  genuinely completed session, not just first-time completions, so
  `LessonGroupCompletion.completed_at` — which only ever fires once, on
  first completion — would have undercounted replay/review days). Known
  approximation: a session that reached `ended_at` but was flagged
  `real_completion = False` server-side (engine ran but didn't reach a
  graded "done" — a narrow edge case) would still count here; accepted since
  there's no stored column to distinguish it retroactively, and it doesn't
  affect the *current* streak/freeze logic, only this calendar's display.
  `start_date` is `user.created_at` in the user's local tz.
- `router.py`: `GET /learning/streak/calendar`, same auth pattern as the
  other `/learning/*` routes. Syntax-checked with `py_compile`; not run
  against a live DB this session.

**Frontend** (`ustadapp/mobile/`):
- `src/types/api.ts`: `StreakCalendar` type.
- `src/api/index.ts`: `learningApi.streakCalendar()`.
- `src/components/StreakCalendar.tsx` (new): renders one month grid per
  month from `start_date` to today, weekday header + flame-above/date-below
  cells. Orange flame (`orange_fire_30.png`) only on dates present in
  `practiced_dates`; every other in-range date gets the blank/unlit flame
  (`blank_fire.png`) — nothing invented for missed days. Dates before
  `start_date` or after today render as a bare, muted date number with no
  flame image at all (rather than implying a flame state that was never
  observed).
- `StreakScreen.tsx`:
  - Hero section changed from stacked/centered (Lottie animation, then
    number, then label, all centered) to a left/right row: streak number +
    "day streak!" on the left, the fire Lottie animation on the right, per
    the layout the user asked for explicitly.
  - Removed the single-active-week "straight line" flame row entirely (the
    7-icon `weekCard` + its now-dead `weekNum`/`weekDayNumbers` calc) —
    superseded by the new full calendar below it.
  - Added `<StreakCalendar>` in its place, fed by a new `useEffect` that
    calls `learningApi.streakCalendar()` on mount; renders nothing if the
    call hasn't resolved yet or fails (no placeholder grid).
  - "Streak Milestones" card (the `+20/+50/+100/+250 XP` reward badges —
    the closest match on this screen to the "+10/+20/+30 XP" the user
    wanted hidden) is now gated behind `const SHOW_STREAK_MILESTONES =
    false` at the top of the file, per "hide, don't remove from wired."

Verified with `npx tsc --noEmit` (clean) and `npx eslint` on all four touched
frontend files (only pre-existing warnings/one pre-existing
`exhaustive-deps` error on an untouched `useEffect`, nothing new). Not yet
run in a real build/emulator — this session was source-only; UI verification
in the running app is still needed before this ships.

## Streak calendar follow-up: real freeze (blue) days, not just practiced days

User asked to reconstruct freeze days too rather than leave them blank
forever. Rather than write a second, separate copy of the freeze/repair
rules to replay historically (risk of the reconstruction quietly drifting
from what the live app actually decides), the replay reuses the exact same
pure functions the live endpoints already call:

- **`ustadAppBackend/app/learning/service.py`**: added
  `_replay_streak_calendar()` — walks the user's `LessonSession(ended_at,
  lesson_group_id)` history one calendar day at a time from signup to today,
  calling the *existing* `_decide_streak()` (for days with a session) or
  `_streak_view()` (for days without, probed as of that day) exactly the way
  `complete_session()` and `/learning/me` already do, carrying state forward
  in a throwaway, never-persisted `_ReplayState` dataclass. Matches the
  pattern `tests/test_streak.py`'s `FakeStreak` already uses for testing
  these same pure functions without a DB. A day counts as "practiced" only
  if some session that day set `decision.advance_activity` — a day where the
  user practiced but only made *partial* repair progress (didn't hit
  `repair_levels_required` distinct groups) now correctly shows as frozen,
  not practiced, matching what the live freeze banner would have said that
  day. `get_streak_calendar()` now calls this and returns both lists.
- **`schemas.py`**: `StreakCalendarOut` gained `frozen_dates: list[str]`.
- **`router.py`**: unchanged (same endpoint, richer response).

Verified against 5 hand-built scenarios in a throwaway script (consecutive
streak, freeze-then-full-repair, freeze-expires-unrepaired,
account-created-before-first-practice, freeze-with-only-partial-repair) —
all 5 matched the expected practiced/frozen split by directly replaying
`_decide_streak`/`_streak_view`. Also re-ran the project's own
`tests/test_streak.py` (18 tests) unchanged to confirm nothing about the
existing pure functions was touched — only a new caller was added. Not run
against a live DB / real user history this session.

**Frontend**: `StreakCalendar.tsx` and `StreakScreen.tsx` now pass/render
`frozenDates` with the existing blue `blue_fire_30.png` icon (same asset
already used for the frozen-streak Lottie/help-modal elsewhere on this
screen) — no new art needed. `types/api.ts`'s `StreakCalendar` type gained
`frozen_dates: string[]`.

## Map: level action card now dismisses on map scroll

The "start a new level" / "repeat the lesson" card could only be closed with
its ✕. Added `dismissActionCards` (clears both `retryNodeId` and
`startPrompt`) wired to the map ScrollView's `onScrollBeginDrag`, so
dragging the map closes an open card instead of leaving it anchored to a
node you've scrolled past.

Deliberately NOT a full-screen tap-outside backdrop, which is the usual way
to do this. The card isn't a Modal — it renders inline, absolutely
positioned inside the map's own `Animated.ScrollView` — so a backdrop would
sit over the map and swallow the first tap. That would regress the path that
already works today: `handleNodePress` clears the other card's state, so
tapping node B while node A's card is open already swaps them in ONE tap; a
backdrop would make that take two. It also risked intercepting scroll
gestures on the app's most scroll-heavy screen.

`onScrollBeginDrag` (not `onScroll`) specifically, for two reasons: it fires
once per drag rather than per frame, and it does NOT fire for programmatic
scrolls — so the viewport auto-following Lumo, and chapter paging, won't
dismiss a card the user just opened. Both setters are no-ops when nothing is
open (useState bails out on an unchanged value), so an ordinary scroll costs
nothing.

Still open, deliberately deferred until this is felt in the app: tapping
empty grass/road doesn't dismiss, and `startPrompt` doesn't toggle closed on
re-tapping the same node the way `retryNodeId` does.

`tsc --noEmit` clean; `eslint` on MapScreen.tsx shows only the 11
pre-existing errors (unused vars, exhaustive-deps on untouched effects) and
no new ones. Not run in the emulator this session.
