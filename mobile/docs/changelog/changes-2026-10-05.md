## Root cause: the false "You're offline" banner

**Symptom:** the banner reads "You're offline. Changes will sync once you're
back online." on app open, while the app demonstrably works.

**Cause: a last-writer-wins race, not a connectivity problem.** Two
independent writers set `isOffline`, on two different timeouts, and they are
not ordered.

1. `SplashScreen.tsx:76` fires `void healthCheck().then(ok => setOffline(!ok))`
   on mount. `healthCheck()` (`api/client.ts:212`) aborts after **5 s** and
   returns `false` on any throw, including its own abort.
2. `RootNavigator.tsx:81` fires `void hydrate()` in parallel. That path uses
   the normal client timeout of **30 s** and sets `isOffline: false` on
   success (`authStore.ts:284`).

The backend is serverless and cold-start-prone — warming it is the stated
reason `healthCheck()` is called from Splash at all (see the comment at
`SplashScreen.tsx:69-75`). A cold start that takes longer than 5 s makes
`healthCheck()` abort and report offline **even though the same backend then
answers `hydrate()` fine a moment later**. Whichever promise settles last
wins, so a cold start reliably produces a stuck banner.

**Why it then stays stuck:** the only thing that clears `isOffline` mid-session
is `refreshLearning()` (`authStore.ts:566`), and it is gated three ways —
`user?.email_verified` must be true, a token must exist, and
`LEARNING_ME_INTERVAL_MS` is 60 s. A signed-out, guest, or unverified user has
nothing that will ever clear the flag for the rest of the launch.

Both writers also conflate "the request failed" with "the device has no
network". `refreshLearning()`'s catch sets `isOffline: true` for *any*
non-401 error (`authStore.ts:576`), so a single 500 or a malformed response
raises an offline banner on a device with perfect connectivity.

**Fixed, see the next section.**

## Connectivity rebuilt: one boolean with five writers → two flags with one each

`@react-native-community/netinfo` 12.0.1 added. Autolinking picks it up for
both platforms (`npx react-native config` confirms `android: true, ios: true`).
`ios/Podfile.lock` does not list it yet, which is expected and needs no manual
step: `eas build --platform ios` runs `pod install` on the EAS macOS worker.

### The shape of the fix

The old `authStore.isOffline` was a single boolean written from five places on
three uncoordinated timers, with no ordering between them. It is replaced by
two flags in a new `store/connectivityStore.ts`, each with exactly one owner:

| Flag | Owner | Means |
|---|---|---|
| `isDeviceOffline` | `services/connectivity.ts` (netinfo, i.e. the OS) | No network at all |
| `isServerUnreachable` | `api/client.ts`, status 0 only | Device has a network, backend gave no HTTP response |

The third case the old boolean swallowed — the server answered, but with a
500/503/404, or a 200 whose body was not valid JSON — now sets neither flag
and raises no connectivity banner. That was the loudest false positive.

### New files

- **`src/store/connectivityStore.ts`** — the two flags. Both default to
  `false` (optimistic): netinfo's first event lands within a tick, and
  defaulting to "offline" would flash the banner on every healthy cold start,
  which is the bug being replaced. Setters are no-ops when the value is
  unchanged, so subscribers do not re-render on repeat writes.
- **`src/services/connectivity.ts`** — the single writer of
  `isDeviceOffline`. Idempotent `startConnectivityWatch()` so Fast Refresh
  cannot stack listeners. Also exports `describeConnection()` for crash
  breadcrumbs (`wifi 72%` on Android, `cellular 4g`, and plain `wifi` on iOS
  since Apple exposes no RSSI to apps) and a one-shot `fetchIsDeviceOffline()`.

  Deliberately **not** configured with our own `/health` as
  `reachabilityUrl`. That would recreate this exact bug inside the library: a
  cold-starting serverless function would again decide whether the user is
  "offline". netinfo's default probe is a tiny always-warm endpoint, and on
  Android `useNativeReachability` (default true) means the OS answers and no
  URL is called at all.

  `isInternetReachable === null` means "not yet determined" and is explicitly
  **not** read as offline. Only `type === 'none'` or an explicit `false`
  counts.

### Changed files

- **`src/api/client.ts`** — all four status-0 throw sites now route through
  one `throwUnreachable(isAbort)` helper, so a future status-0 site cannot
  forget to flag reachability. A matching `markReachable()` fires the moment
  any HTTP response arrives, whatever its status, since a 500 proves the
  backend is reachable. `healthCheck()` is now warming-only and its flag write
  is one-directional: success records reachability, a 5s timeout records
  nothing, because that fuse is shorter than the cold start it exists to hide.
- **`src/store/authStore.ts`** — `isOffline` and `setOffline` removed, along
  with all five assignments. `refreshLearning`'s catch no longer writes any
  connectivity flag; it just adds a breadcrumb, now including the status.
- **`src/screens/startup/SplashScreen.tsx`** — `void healthCheck().then(ok =>
  setOffline(!ok))` became `void healthCheck()`. Warming is its only job.
- **`src/components/OfflineBanner.tsx`** — reads the two new flags, with
  device-offline taking precedence. **Copy changed, needs review:** the old
  single message was "You're offline. Changes will sync once you're back
  online." Every clause of that could be false at once, and the sync promise
  was never true in any case, since there is no write queue behind this
  banner. Now:
  - device offline: "You're offline. Some things may be out of date."
  - server unreachable: "Can't reach Ustad right now. Some things may be out
    of date."

  Both avoid dash punctuation per the standing copy rule.
- **`App.tsx`** — starts the watcher once, above the navigator, so signed-out
  and guest launches are covered. The old detection only ran on Splash and
  could never clear itself mid-session for an unverified user.
- **`jest.setup.js`** — netinfo mock, defaulting to a healthy wifi state.

## App version: five disagreeing sources → one

The Profile screen's version label was effectively frozen. `utils/appVersion.ts`
read `process.env.VERSION_NAME ?? '1.0.0'`, and that env var is only ever
exported by one workflow, so the hardcoded fallback was what most builds
actually shipped.

The version was declared in five places, all of which said `1.0.0` while
Android had shipped through **1.0.33**:

| Where | Was | Used by |
|---|---|---|
| `package.json` version | 1.0.0 | `services/usageSession.ts` (analytics) |
| `utils/appVersion.ts` fallback | '1.0.0' | Profile label |
| `android/app/build.gradle` fallback | "1.0.0" | native versionName |
| `app.json` expo.version | 1.0.0 | EAS / Expo tooling |
| `ios` pbxproj `MARKETING_VERSION` | 1.0.0 | CFBundleShortVersionString |

Two consequences, both real:

- **Every iOS TestFlight build shipped stamped 1.0.0.** No iOS workflow
  exports `VERSION_NAME` and `MARKETING_VERSION` was hardcoded, so builds
  20040 and 20042 are both logged as `1.0.0` in this changelog's own version
  log while the equivalent Android build was 1.0.33. App Store Connect saw
  1.0.0 for all of them.
- **Analytics and the UI disagreed.** `usageSession.ts` read `package.json`
  directly while `appVersion.ts` read the env var, so `app_version` in
  analytics and the string on Profile could differ in the same build.

### The fix

`package.json` is now the single canonical source, bumped once per release
(`npm version <x.y.z>`), and set to **1.0.34** to match what has actually
shipped.

- **`src/utils/appVersion.ts`** — falls back to `package.json`'s version
  instead of a hardcoded literal. `VERSION_NAME` still wins when exported, so
  CI behaviour is unchanged; the worst case is now the real release number
  rather than a frozen string.
- **`src/services/usageSession.ts`** — imports `APP_VERSION` from
  `utils/appVersion.ts` instead of reading `package.json` itself. One source,
  so analytics and the label cannot drift apart.
- **`android/app/build.gradle`** — versionName falls back to the version
  parsed out of `package.json`. Uses `java.util.regex` explicitly rather than
  Groovy's `=~`, because a Groovy Matcher in a boolean context calls `find()`
  and advances itself, which makes the obvious one-liner quietly wrong.
- **`scripts/sync-version.mjs`** (new) — pushes `package.json`'s version into
  the two targets that cannot read it themselves: `app.json`'s `expo.version`
  and every `MARKETING_VERSION` in the pbxproj (all build configurations, not
  just the first). `--check` reports drift and exits 1, for CI. Deliberately
  does **not** touch build numbers: those are per-build, CI owns them, and
  conflating the two is what caused the 10039 collision that hung an App
  Store submission for about an hour.
- **`package.json`** — new `sync-version` script, and `build:apk` / `build:aab`
  now run it first, so a release build cannot produce an artefact whose native
  version disagrees with the bundle.

`app.json` and the pbxproj are now synced to 1.0.34.

### Lockfile: hit the known npm 11 regression, then fixed it

Installing netinfo with the local npm (11.9.0) dropped the package count from
**1455 to 1452** — the same nested-peer-entry loss that failed `npm ci` in CI
at 16 s during the 20042 build, recorded in the version log. Regenerated with
the documented workaround, `npx npm@10 install --package-lock-only`, giving
**1456** (1455 plus netinfo) and a 13-line diff that adds only the new
dependency. Worth remembering that the local npm is still 11.x, so any future
dependency change needs the same follow-up.
