# Changes 2026-09-28

## Fixed: map HUD (`MapScreen.tsx`) — stretched streak pill, oversized search button, squashed mountain band

**Report:** on-device screenshot (latest build, `26092516`/1.0.32) across
multiple phones — streak pill rendered as a wide, mis-shapen bar instead of
its normal compact pill, the search button (below it) was too large, and the
mountain skyline band above the map looked squashed/thin.

**Root cause:** the 2026-09-22 change that bumped the search button from
64px to 96px put it in a plain `<View>` column above the streak pill with no
`alignItems` set. React Native's default `alignItems: 'stretch'` then
stretched the streak `TouchableOpacity` (normally sized to its own content —
flame icon + 1-2 digit number) out to match the wider 96px search button
below it, warping the rounded pill into an elongated bar. The oversized
search button also added ~32px more to the measured `hudHeight`, which
directly shrinks the mountain image's visible window (`SKY_BOUNDARY_Y + 28 -
hudHeight`) — squashing the mountain band thinner than intended. (The
2026-09-22 entry's mountain-crop investigation was real but was masking this
simpler, larger effect from the same change.)

**Fix:**
- Added `alignItems: 'flex-start'` to the streak-pill/search-button column
  `View` so the streak pill hugs its own content again instead of stretching.
- Search button is no longer a fixed 96px. It's now sized to exactly match
  the streak pill's own measured width (`streakPillWidth`, captured via
  `onLayout` on the pill, both edges therefore flush on every screen width
  instead of a hardcoded constant that only happened to line up on some
  devices) — smaller than before per request, and self-correcting for
  "ruined on some phones but not others" since it now derives from the
  pill's real rendered size rather than a guessed pixel value.
- Mountain band should return to its normal height as a direct consequence
  of `hudHeight` shrinking back down; not a separate change.

## Added: leaderboard avatars (`LeaderboardScreen.tsx`) — replaced emoji with illustrated characters

**Report:** user supplied `leaderboard_characters.zip` (Downloads) containing 5 full-body
character SVGs (`gee_me_001/002/032/082/083`) with instructions to use them on the
leaderboard instead of the current 👧/👦/🧑 emoji avatars, and make sure they fit and
are all the same size.

**Source art prep:** the SVGs are full-body standees (viewBox aspect ratios
0.36–0.50, i.e. much taller than wide) at wildly different native canvas sizes
(1022×2813 up to 1951×3898) — unusable directly in a 38px list-row circle.
Rasterized each with `sharp` (already a project devDependency) and cropped to a
head/shoulders bust (top ~44–46% of full height; 082 needed a top offset of 8%,
see below) at 400px width, saved as PNGs in the new
`assets/characters/leaderboard/` folder: `lb_male_1/2.png` (001, 083 — read as
male by outfit/features), `lb_female_1/2/3.png` (002, 032, 082 — read female).

**Found in the source art:** `gee_me_082.svg` has a stray skin-colored rounded
rectangle (`x=542 y=96 w=1081 h=1279`) whose top corners poke out above the
hairline — a pre-existing defect in the file as supplied, not introduced here.
Worked around by starting that character's crop 8% further down (past where
the hair fully covers it) rather than editing the vector art itself.

**Mapping (per user's explicit answers):** male gets a per-user stable pick
between the 2 male-read characters; female between the 3 female-read
characters; gender unset (common — see backend `leaderboard/service.py`) picks
from the full pool of all 5, same mechanism. "Stable" = hashed off
`display_name` (same 31-multiplier hash `utils/avatar.ts`'s `stablePickIndex`
already uses, just keyed on name instead of user id) — `LeaderboardEntry` (the
leaderboard API response) carries no user id, so there is no way to make this
match the same person's actual Welcome/Profile avatar (`utils/avatar.ts`'s
`characterSrcFor`, a completely separate, already-existing system keyed on
user id + an explicit `avatar_variant` pick). Flagged to the user as a known
gap, not something in scope to fix here (would need a backend change to
expose user id/variant on the leaderboard response).

**Fit/sizing:** podium avatars are now `46px`/`58px` (rank 1) circles,
row-list avatars stay the existing `38px` circle — all rendered via
`resizeMode="cover"` inside a fixed-size `overflow: hidden` circle, so every
avatar reads as the same size and fully fills its circle regardless of each
source PNG's own (slightly varying, ~0.8–1.1) aspect ratio, instead of the
old approach of trusting a font-sized emoji glyph's natural box.
