## Batch 1 — error handling (from the QA pass)

Seven fixes, all for cases where a failure had no handler and the user got no
error, no retry and no crash report.

### `src/utils/storage.ts`

- Added a `safeJsonParse<T>()` helper and routed all four unguarded
  `JSON.parse` reads through it (`getTokens`'s legacy migration,
  `getStoredUser`, `getOnboarding`, `getUnlockedSeasons`). Three of those sit
  on the `hydrate()` critical path, so a truncated AsyncStorage value (process
  killed mid-write, disk full, OS migration) threw, `isHydrated` never flipped,
  and the app sat on Splash **forever**, silently.
- Moved `tokensInFlight = null` from the success path into a `finally`. Any
  throw used to strand a *rejected* promise there, which every later
  `getTokens()` call re-received — permanently un-authenticating every request
  for the life of the process. Also wrapped the body so a Keystore failure
  reports "signed out" rather than rejecting.

### `src/store/authStore.ts`

- Split `hydrate()` into a thin `try/catch` wrapper around a new
  `hydrateInner()`. `RootNavigator` calls it as a bare `void hydrate()` and
  `isHydrated` is the only thing that moves the app off Splash, so a rejection
  anywhere in it was an unrecoverable hang. The flag is now always set and the
  error is reported.
- Added the missing `setCrashUser(user.id, user.email)` inside `hydrateInner`.
  It was called in login/register/guest/upgrade but **not** in hydrate, which
  is the path every returning user takes on every cold start — so the majority
  of real crash reports arrived anonymous and Crashlytics' "users affected"
  count was meaningless.

### `src/screens/lesson/LessonSessionScreen.tsx`

- `submitAnswer`'s catch handled `404`, `400` and status `0` only. Every other
  status (500, 502, 422, 403, rate limits, an unrecoverable token refresh) fell
  through every branch: `setSubmitting(false)` re-enabled the Check button and
  **nothing else happened**. No feedback, no way forward but force-closing the
  app, and nothing reported. Added the missing `else`: `captureError` with the
  exercise context, then the same exit the no-connection branch already offers.
  New copy contains no dashes, per the house rule.

### `src/services/crashReporter.ts`

- Six call sites used `void crashlytics().someAsyncMethod()` inside a
  `try/catch`. A bare `void p` does **not** catch an async rejection — the try
  block exits the moment the promise is created. Every one was a latent
  unhandled rejection, which is especially bad in the module that installs the
  global error handler. Added an `ignore()` helper that attaches a real no-op
  catch.

### `src/services/contentCache.ts`

- Wrapped `writeEntry`. `readEntry` already treated any failure as a miss;
  `writeEntry` did not, so a full disk discarded a response the caller had
  already fetched (`loadSurahs`/`loadLessonGroup` await it after the network
  call) and turned bootCache's `void setCachedLevelsToDisk(...)` into an
  unhandled rejection.

### `src/utils/streak.ts`

- Wrapped `checkStreakLoss`. It is reached from `applyFreshLearning`, which
  `hydrate()` awaits, and its `AsyncStorage.setItem` was unguarded. Losing one
  streak-lost popup beats not starting the app.

## Batch 2 — iOS submission readiness

Everything here is fixable from Windows. **`pod install` still has to be run on
a Mac** — see "Still blocked" below.

### `ios/Podfile`

- Added `$RNFirebaseAnalyticsWithoutAdIdSupport = true`. CocoaPods was
  resolving `FirebaseAnalytics/IdentitySupport`, making the binary capable of
  reading the IDFA while `PrivacyInfo.xcprivacy` declared
  `NSPrivacyTracking = false` with no `NSUserTrackingUsageDescription`. That
  mismatch is a routine App Review rejection.

### `ios/UstadApp.xcodeproj/project.pbxproj`

- `TARGETED_DEVICE_FAMILY` `"1,2"` → `1` (both configurations). The project
  claimed iPad while `AppIcon.appiconset` has no iPad sizes (76pt, 83.5pt), so
  App Store Connect would reject the upload outright. The UI is phone-designed
  anyway; iPad users still get the phone app.
- `MARKETING_VERSION` `1.0` → `1.0.0`, to agree with Android's `VERSION_NAME`.
- Added an **"Upload Crashlytics dSYMs"** run-script phase, last in the
  target's `buildPhases` so the `.app` and its dSYM both exist by then.
  Without it, iOS crash reports are raw addresses rather than function names.
  The script is guarded: if `${PODS_ROOT}/FirebaseCrashlytics/run` is missing
  (i.e. before `pod install`) it prints a warning and exits 0 instead of
  failing the build with a confusing "No such file or directory".

  Verified structurally: braces/parens balance, all 51 referenced object ids
  are defined, all 11 sections pair, and the embedded script round-trips to
  valid shell (`bash -n`) and behaves correctly when the pod is absent.

### `ios/UstadApp/PrivacyInfo.xcprivacy`

- `NSPrivacyCollectedDataTypes` was an **empty array**. Filled in with the
  eight types the app actually collects: email, name, user id, age/gender,
  **audio recordings**, product interaction, crash data, performance data. All
  marked Linked (the account is authenticated) and all `Tracking = false`
  (no ad networks, no brokers, no cross-app correlation), consistent with
  `NSPrivacyTracking = false`.
- Added the `DiskSpace` accessed-API declaration (`E174.1`) that AsyncStorage
  and the audio cache need.
- **The App Store Connect App Privacy questionnaire must be answered to match
  this file.**

### `ios/UstadApp/AppDelegate.swift`

- Added `application(_:open:options:)` forwarding to
  `GIDSignIn.sharedInstance.handle(url)`. Without it the Google sheet completes,
  redirects to our custom scheme, and nothing is listening — so
  "Continue with Google" could never return a token on iOS. Unlike Firebase,
  GIDSignIn does not swizzle the app delegate, so the app must forward it.
- Made the missing-`GoogleService-Info.plist` case **loud**. It previously
  skipped `FirebaseApp.configure()` in silence, which is why iOS had no
  Crashlytics, no Analytics and no Google Sign-In with no symptom. Now it
  `NSLog`s a banner naming all three and the fix. Deliberately logged and not
  asserted, so a contributor without Firebase credentials can still build.

### `scripts/link-firebase-ios.mjs`

- Now does two jobs instead of one. Alongside registering the plist as a bundle
  resource, it reads `REVERSED_CLIENT_ID` out of `GoogleService-Info.plist` and
  writes the `CFBundleURLTypes` block into `Info.plist`. That value is
  project-specific and lives only in the uncommitted plist, so it cannot be
  committed by hand — generating it is the only way to keep it correct.
- An existing Google scheme is matched by its `com.googleusercontent.apps.`
  prefix and **replaced**, so re-running after a Firebase project change swaps
  the scheme rather than leaving a stale second one (two schemes means the OS
  picks one, and half the time it is the wrong one).
- Warns clearly and skips if `REVERSED_CLIENT_ID` is absent, which means Google
  Sign-In has not been enabled for the iOS app in the Firebase console.

  Verified against a synthetic `GoogleService-Info.plist`: produces a
  `plistlib`-parseable `Info.plist`, is idempotent across three runs, and
  correctly replaces a scheme when the project id changes.

### `firebase.json` (new file, repo root)

React Native Firebase reads per-app config from this file and it did not exist,
so the iOS build script was printing *"A firebase.json file was not found"* and
injecting an empty config on every build.

```json
{
  "react-native": {
    "crashlytics_disable_auto_disabler": true,
    "crashlytics_javascript_exception_handler_chaining_enabled": true,
    "google_analytics_automatic_screen_reporting_enabled": false
  }
}
```

- **`crashlytics_disable_auto_disabler: true` is load-bearing.** Adding a
  `firebase.json` *without* it would have made iOS worse, not better: the RNFB
  build script injects `FirebaseCrashlyticsCollectionEnabled = NO` into
  Info.plist whenever it finds a firebase.json that does not set this flag, so
  any native crash before JS boots and calls
  `setCrashlyticsCollectionEnabled(true)` would be lost.
- `google_analytics_automatic_screen_reporting_enabled: false` stops Firebase's
  automatic `screen_view` (which reports the single native host controller /
  `MainActivity`) from competing with the real screen names `RootNavigator`
  already logs via `logScreenView`. **This affects Android too.**

### `src/services/secureTokens.ts`

- `ACCESSIBLE.WHEN_UNLOCKED` → `ACCESSIBLE.WHEN_UNLOCKED_THIS_DEVICE_ONLY`.
  Without `THIS_DEVICE_ONLY` the keychain item is included in encrypted device
  backups and restores onto a *different* device, carrying a live access +
  refresh token pair with it.

### `src/services/audioPlayer.ts`

- Fixed the iOS earpiece bug. `setCategory` is a **process-wide**
  AVAudioSession setting, and `react-native-audio-recorder-player` leaves the
  session in `PlayAndRecord` after a speak exercise, which routes output to the
  receiver. `playAudioUrl`'s **preloaded fast path** never re-asserted
  `Playback` — and that is the path a real lesson always takes, because
  `loadGroup` preloads every clip up front. So after the first speak exercise,
  every subsequent ayah played quietly out of the earpiece for the rest of the
  lesson. Android ignores the category entirely, which is why device testing
  there never surfaced it.
- Extracted `ensurePlaybackCategory()` and called it from all four playback
  entry points (preloaded path, `resumeAudio`, `playFeedbackSound`, and the
  existing lazy-load path).
- **Needs verifying on a real iPhone.** Do a speak exercise, then immediately
  play an ayah, and listen for whether it comes from the speaker.

### `package.json`

- `version` `0.0.1` → `1.0.0`. `services/usageSession.ts` reads this as
  `app_version` on every `POST /usage/sessions`, so every row was recording
  `0.0.1` and releases were indistinguishable in your own analytics.

3. `cd ios && pod install`.
4. Build, then check the build log for the "Upload Crashlytics dSYMs" phase.
