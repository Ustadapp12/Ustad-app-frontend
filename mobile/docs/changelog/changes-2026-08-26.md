## 1. Map: recommended-next node highlighting — `src/screens/home/MapScreen.tsx`

Users were tapping the Lumo mascot expecting it to start the level, since it
stood beside the recommended node with a "Begin here!" / "Ready for today's
lesson?" speech bubble that read like an instruction pointing at whatever was
biggest and most animated on screen — which was Lumo, not the actual node.
Root gap: the recommended node had **no visual distinction at all** from a
genuinely locked node besides the 🔒 icon; a pre-existing pulse-ring
animation existed but was scoped to special/review nodes only.

- `MapNode` gained an `isRecommended` prop; `isPulsing` now fires for
  `isSpecial || isRecommended` (previously `isSpecial` only) — the same pulse
  ring specials already had now also marks the recommended node, no new
  asset needed.
- Pulse ring color is no longer a hardcoded green (`#37A168`) — it now
  matches whichever art the node is actually showing: `colors.nodeLockedBorder`
  (grey) for regular nodes rendering `node_locked.png`, `colors.primaryLight`
  (green) for special nodes rendering `special.png`. `special.png` /
  `special_done.png` node-art logic itself is unchanged.
- Removed the `<LumaFloat>` render + its speech bubble from beside the active
  node, along with the now-dead derived positioning (`lumaLeft`, `lumaTop`,
  `scrollIsLeft`, `lumaSpeech`, `lumaSpeechTailAngle`). Lumo still renders
  elsewhere (season-gate unlock messages) — untouched.
- Explicitly did **not** change the "recommended next" concept itself:
  `firstActiveNode`, the auto-scroll-to-node effect, and `jumpToRecommended`
  are all unchanged — tapping the map / the node still goes to the same
  recommended level as before. Only the visual cue changed.

## 3. Android bottom-nav padding — real fix, not a flat floor

Previous fix (`MIN_SAFE_BOTTOM = 48`, added because
`useSafeAreaInsets().bottom` was confirmed misreporting as 0 on some real
3-button-nav devices) had a real flaw only caught this session: `Math.max`
can't tell "device correctly reporting a small ~8–24dp gesture-nav inset"
apart from "device incorrectly reporting 0" — both are less than 48, so both
got forced up to the same padding. That meant every gesture-nav Android
phone (the majority of the fleet) and iOS (which never had this bug at all —
UIKit's safe-area insets are reliable, not a JS-bridge relay) were getting
unnecessary bottom padding.

- **New:** `android/app/src/main/java/com/ustadapp/UstadNavigationBarModule.kt`
  — a native module that reads the real nav-bar height straight from
  Android's own `WindowInsetsCompat.Type.navigationBars()` API, independent
  of the `react-native-safe-area-context` JS bridge that was confirmed
  misreporting. Returns 0 on gesture-nav / no-bar devices (correct — nothing
  to clear), the true measured bar height on 3-button devices. Exposed as a
  blocking synchronous `@ReactMethod` (`getNavigationBarHeightDp()`) since
  `safeBottomInset()` is called inline during render across 26 screens and
  can't become async.
- **New:** `android/app/src/main/java/com/ustadapp/UstadNavigationBarPackage.kt`
  — registers the module.
- `android/app/src/main/java/com/ustadapp/MainApplication.kt` — added
  `add(UstadNavigationBarPackage())` to the manual package list.
- `src/utils/responsive.ts` — `safeBottomInset()` rewritten: on iOS, returns
  the real inset untouched, always, no floor. On Android, floors
  `insets.bottom` up to the natively-measured real value (cached after first
  read) instead of the flat `48` constant, which is removed entirely. Every
  one of the 26 screens that call `safeBottomInset()` picks this up
  automatically — nothing per-screen to change.

Caught one native compile error before it shipped: `currentActivity` isn't
directly inherited on `ReactContextBaseJavaModule` in this RN version —
fixed to `reactApplicationContext.currentActivity`.

## Open investigation, no code changed: Google Sign-In `DEVELOPER_ERROR` via Play Console Closed Testing

Confirmed still live via Crashlytics (real event 2026-08-24, two different
device models over 60 days — not one flaky handset). Works when sideloaded
with the identical Play App Signing certificate; fails specifically for
testers installing through the real Closed Testing Play Store listing
(confirmed not an Internal App Sharing mix-up — different signing cert
mechanism, ruled out).

Leading unresolved thread: Cloud Console's OAuth client shows "App ownership
verification: not applicable... not a Google Play Store app" — found the
same exact stuck status independently reported by another developer whose
app was also already correctly published with a matching SHA-1, with no
public resolution beyond Google Cloud Support. Google's own docs frame
ownership verification as anti-impersonation/branding, not a documented
requirement for the sign-in flow itself, so this remains suggestive, not
confirmed as the cause. Full history: `project_handoff_0825_google_signin.md`
in memory.

**Still the single most decisive untried test:** pull the actual
Play-Store-installed APK from a currently-failing device and check its cert
directly (`adb shell pm path com.ustadapp` → `adb pull` → `apksigner verify
--print-certs`), rather than trusting Play Console's displayed cert or a
freshly-built local artifact.

## 5. Guest mode: consistent "not saved" everywhere

number, sometimes not) and traced it to a backend quirk: guests' streak
`last_active_at` is never persisted (by design — XP/streak aren't banked
until signup), so the day-gap calculation always takes the "no history"
branch and reports `current_streak: 1` on every single completion, forever
— never a real accumulating count. Decision (confirmed with the user):
don't fix the backend to accumulate — instead make every guest touchpoint
consistently show "not saved" rather than a fake incrementing number.

## 10. SoLoader crash investigation (no code change)

Queried Crashlytics fresh (not from memory) for the top FATAL Android issue:
`SoLoaderDSONotFoundError: couldn't find DSO to load: libreactnative.so` in
`MainApplication.onCreate`, present in every release since 1.0.0. Traced it
to PC/Android-emulator users (BlueStacks/LDPlayer/NoxPlayer-style), not real
phones — those emulators run on real x86_64 host CPUs with an ARM-translation
layer that makes `Build.SUPPORTED_ABIS[0]` report x86_64 (native) ahead of
arm64-v8a (translated); SoLoader resolves against slot `[0]` and this app
deliberately ships no x86_64 native libs (by design, to keep the APK smaller
for real phones), so it crashes instead of falling back to the working
arm64-v8a set. All 9 impacted users in the sampled window shared the
identical "OnePlus 8 Pro / Android 11" device signature — a strong tell for
"many installs of the same emulator profile," not distinct real phones.
Decision (confirmed with the user): accept as a known limitation, no fix.
Recorded in memory (`project_soloader_crash_emulator.md`) so this doesn't
need re-investigating from scratch later.
