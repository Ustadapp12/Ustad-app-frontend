## Connectivity: hardened the launch path

`startConnectivityWatch()` ran unguarded inside a `useEffect` at the top of
the tree in `App.tsx`. netinfo is a native module, and React Native's
NativeModules proxy throws on access when the native side did not link — the
exact failure this app has already seen in the wild via SoLoader on emulator
installs. An exception there would have dropped every launch to the
ErrorBoundary screen, which is a far worse bug than the stuck banner being
fixed.

Both `startConnectivityWatch()` and `stopConnectivityWatch()` are now
non-throwing. If netinfo is unavailable the watch is simply never installed, a
breadcrumb records why, and the app behaves exactly as it did before the
module existed. The teardown drops its reference in a `finally`, so a failed
native unsubscribe cannot leave the watch permanently un-restartable.

## Search list: open/closed/done now means something

The list showed two states, and the mapping was wrong for the question the
screen is meant to answer.

**Finding that reshaped this.** `firstLevels` can only ever return
`completed`, `in_progress` or `available` — never `locked`. The backend is
explicit about it in `learning/service.py`'s `get_first_levels_for_surahs`:
*"A surah's first group has no cross-surah gate — never locked."* So an
availability-based badge marks all 114 surahs open and conveys nothing, and
there is no server-side lock to toggle.

The rule is therefore keyed off completion, per explicit product decision:

| State | Means | Rendering |
|---|---|---|
| `done` | every level complete | green, "Done" tag |
| `open` | first level complete, surah genuinely underway | gold, "Open" tag |
| `closed` | first level not complete | grey row, greyed text, "Closed" tag |
| `unknown` | status could not be loaded | no tag at all |

`unknown` is deliberately a first-class state. `statusBySurah` starts empty
and the fetch can fail, so treating absence as "closed" would have labelled
all 114 surahs closed on any network hiccup, telling a user their finished
work was gone. Rows stay untagged until the load actually succeeds.

### How `done` is resolved

`firstLevels` returns only the first level, so it cannot tell "started" from
"finished", and there is no per-surah completion endpoint (`learningApi.stats`
gives `surahs_completed` as a count, not a list). A second pass calls
`learningApi.levels(n)` — but only for surahs whose first level is already
complete, which is bounded by how many surahs the user has actually started
rather than by 114. The calls run sequentially so they cannot stampede a
cold-start-prone backend, and a failure leaves the surah showing `open`, which
is true but less specific, never claiming completion it cannot prove.

### The confirm step

Tapping a **closed** surah opens the confirm dialog; tapping one already
underway navigates straight through, since re-confirming work in progress is
pure friction.

Confirming navigates to the surah's first level and records nothing. The row
flips to "Open" when that level is actually completed, not on the tap. There
is no backend notion of an unlocked-but-unstarted surah, so a local flag would
disagree with the map and with this screen after a reload, and would fill the
list with "open" surahs the user never touched — defeating the entire purpose
of the badge. `StartSurahModal`'s copy was reworded to match what really
happens ("Open {surah}?", "counts as open once you finish that level") instead
of implying the tap itself opens it.

### Also fixed

The `firstLevels` failure path was a bare `console.warn`, which left every row
silently uncoloured and indistinguishable from a real state. It now sets a
`failed` load state that surfaces an inline "Couldn't load your progress ·
Retry" row. This is very likely what was being seen as unexplained grey rows,
since the same cold-start latency behind the offline-banner bug would make
this call fail too.

`statusRank` was replaced by a `STATE_RANK` table over the four states, and
`stateFor()` is now the single place a row's state is decided, so the list,
the sort and the confirm dialog cannot disagree.
