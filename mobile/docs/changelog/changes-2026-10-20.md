# Changes, 2026-10-20

## An-Nas's very first level read "Jump here" instead of being the map's start

`Map2NodeView.tsx`'s `lookFor()` tagged every surah's first level `'jump'`
("JUMP HERE?") regardless of which surah — including slot 0, An-Nas's level
1, the very bottom/start of the whole map (`map2Model.ts`'s own comment:
"slot 0 = An-Nas level 1 at the very bottom of the map"). For a guest/new
account where that node isn't yet the recognized active slot, it fell
through to the jump branch instead of reading as a plain open node. Fixed
with a `node.slot !== 0` guard so slot 0 falls through to `'open'`/`'current'`
instead.

## iOS bottom tab bar: dark/mismatched seam at the bar's cut corners

The Figma bar's top corners cut away by design to reveal the real screen
color underneath (the "floating card" look). This was implemented by pulling
the bar up over the screen's last 13pt (`marginTop: -CORNER_OVERLAP * s` in
`Map2TabBar.tsx`) and hoping the screen's own background happened to line up
pixel-for-pixel underneath — fragile on iOS, where that overlap is a
fractional (`* s`) value and RN rounds each view's layout to device pixels
independently, so a sub-pixel gap could expose the navigator's dark
`contentStyle` (`#0D1B2A`, meant for the Splash/auth flow) as a visible
outline. Fixed per the user's direction: baked each screen's own real
background (`DailyQuest: '#0D3B26'` gradient edge stop, `Building`/
`Leaderboard: '#F5F7FA'`, `Profile: '#F2F4F8'`) directly into the tab bar's
own wrapper view (`SCREEN_BG` map in `Map2TabBar.tsx`), so the corners reveal
a color the bar paints itself instead of depending on alignment with a
separate sibling view. (`Building`'s entry was later corrected to
`'#F2F4F8'` when `PrayScreen` replaced `BuildingTabScreen` — see below.)

## Backend location storage — built, deployed, mobile now sends it

The backend spec above was implemented by a separate session (PR #56 on
`Ahmad/dev`, migrations applied to prod 2026-10-20 — see
`ustadAppBackend/CHANGES.md`'s own 2026-10-20 entry). Verified live
against the real production API (`ustad-app-backend-six.vercel.app`, the
URL this app actually ships with) via its `openapi.json`: `PATCH /users/
me/location` exists with the documented `LocationUpdateIn` schema, and
`/usage/sessions`' `StartSessionIn` carries optional range-validated
`latitude`/`longitude`.

Wired the mobile side per the user's detailed spec:
- `api/index.ts`: `usageApi.startSession`'s body gains optional
  `latitude`/`longitude`; new `usersApi.updateLocation(lat, lon)`.
- `utils/location.ts`: `getCurrentCoordinates()` now also populates a
  module-level cache on every successful resolve (never populated any
  other way); new `getLastKnownCoordinates()` reads it without ever
  touching permissions or the GPS itself.
- `services/usageSession.ts`: `startUsageSession()` reads that cache and
  includes `latitude`/`longitude` in the session-start body only when a
  fix is already cached — never triggers a fresh GPS read or permission
  prompt itself, since sessions start on login/register/guest/hydrate,
  often before the user has seen the Pray tab.
- `screens/pray/PrayScreen.tsx`: the coordinate-resolution logic moved
  into an exported `loadPrayerData()` (testable as a plain async function,
  matching this repo's existing test style — no component-render harness
  is set up here). On every successful fix it still computes the next
  prayer and qibla bearing as before, and now also fires
  `usersApi.updateLocation()` best-effort (`.catch(() => undefined)`,
  never awaited, never blocks the UI).

New tests: `__tests__/usageSession.test.ts` (+3 — includes lat/lon when
cached, omits both when not, confirms the existing "swallows a failed

## Pray screen: "next prayer" stuck on stale data

Reported: still showed "Fajr 4:53" long after it should have moved on to
Zuhr. Root cause: `PrayScreen.tsx` resolved prayer data once in a plain
`useEffect` on mount, but like every other tab screen in `MainTabs` it
stays mounted across tab switches, so that effect only ever ran once for
the component's entire lifetime -- `next`/`current` never recomputed as
real time passed, regardless of how long the tab was open or revisited.
Fixed with `useFocusEffect` (re-resolves every time the tab regains
focus) plus a 60s interval while focused (keeps it correct even if the
user just leaves the tab open through a prayer-time boundary without ever
navigating away). `tsc --noEmit` clean, full suite still 90 passed.

## Pray screen: stopped re-reading the GPS every 60s

Follow-up to the fix above, per feedback: that first pass had the 60s tick
call the *whole* `loadPrayerData()` again, which re-reads the GPS and
re-pings `usersApi.updateLocation` every minute a user sits on the tab --
real battery/backend cost for no reason, since a location barely changes
minute to minute and prayer boundaries are hours apart. Split the concern
in two: `refetchLocation()` (a real GPS fix via `loadPrayerData()`, which
now also returns the resolved `coords`) runs only on focus; a new
`recompute()` re-derives `next`/`current`/`qibla` from that **cached**
coordinate (plain date math through the existing pure
`nextPrayerFromCoords`/`currentPrayerFromCoords`/`qiblaBearingFromCoords`
-- no GPS, no network) on the 60s tick instead. The hero card's own "NOW"
clock (`HeroSalahCard.tsx`) was already a plain local `setInterval`
independent of this -- confirmed it ticks correctly on its own, no change
needed there. `__tests__/prayScreen.test.ts` updated for `loadPrayerData`'s
new `coords` field. Full suite: 90 passed. `tsc --noEmit` clean.
