# Changes, 2026-10-21

## Qibla compass was off by the local magnetic declination

The compass dial in `screens/pray/QiblaCompass.tsx` rotates using the live
heading from `react-native-compass-heading`, compared against
`utils/qibla.ts`'s `qiblaBearingFromCoords()` (which wraps `adhan`'s
`Qibla()`). `Qibla()`'s bearing is relative to **true (geographic) north**.
Reading `react-native-compass-heading`'s native source directly confirmed
it reports **magnetic** heading on both platforms, uncorrected: iOS's
`CompassHeading.swift` uses `newHeading.magneticHeading` (not
`.trueHeading`) at both call sites; Android's `CompassHeadingModule.kt`
takes the rotation-vector sensor's azimuth straight through, with no
`GeomagneticField` or declination correction anywhere in the file. So the
dial was comparing a magnetic bearing against a true-north bearing
directly — off by the gap between them (magnetic declination), which is
near 0° in some places and 15-20°+ in others, varying by location and
slowly by time.

Fixed with a model-based correction in shared JS, not a native patch (the
same correction needed on both platforms, per the explicit ask). Evaluated
`geomagnetism` (pure-JS port of NOAA's World Magnetic Model) as the first
candidate and it checked out on every count that mattered: actively
maintained (last published December 2024, specifically to add the
WMM2025-2030 coefficient table — i.e. maintained in step with WMM's own
5-year release cycle, not abandoned), zero runtime dependencies, no
Node-only APIs on its require path (`index.js` → `lib/model.js` → `lib/
coords/*` is pure `Math`/`Date`; the WMM coefficient tables are plain `.json`
files pulled in via `require()`, which Metro already supports — the only
file using `fs` is `bin/convert.js`, a build-time script nothing requires
at runtime), and small (~73KB unpacked for five historical+current model
vintages combined). Installed as a real dependency (`npm install
geomagnetism@0.2.0`), not vendored.

New `src/utils/declination.ts` exports `trueHeadingFromMagnetic(magneticHeading,
coords, date = new Date())`: pure function, same shape as `utils/qibla.ts`/
`utils/prayerTimes.ts` (reuses `Coords` from `utils/location.ts`, no I/O or
permission calls inside it). Looks up `geomagnetism`'s `decl` for the given
coordinate/date and returns `(magneticHeading + decl) mod 360` wrapped into
`[0, 360)` — verified the sign convention against the library's own
NOAA reference test vectors (shipped as `test/values.csv` inside the
package) rather than assuming it: declination is east-positive,
west-negative, and true heading is magnetic plus declination. Passes
`allowOutOfBoundsModel: true` to `geomagnetism.model()` so a wildly wrong
device clock falls back to the nearest available WMM table instead of
throwing and killing the compass outright (current table covers
2024-11-13 through 2029-11-13).

Wired into `QiblaCompass.tsx`: the `CompassHeading.start()` callback now
runs the raw `heading` through `trueHeadingFromMagnetic()` before computing
the dial's rotation target, so everything downstream (the shortest-path
0/360 wrap logic, the `Animated.timing` call) operates on true heading as
it always should have. This needed the user's coordinates inside
`QiblaCompass`, which didn't have them before — traced the existing data
flow (`PrayScreen.tsx` already resolves one GPS fix per focus via
`refetchLocation()`/`loadPrayerData()` and re-derives per-tick values from
a cached `coordsRef` via `recompute()`) and threaded `coords` through the
same way `qiblaBearing` already flows: `PrayScreen` gained a `coords` state
variable (set alongside `qibla` in both `recompute()` and
`refetchLocation()`'s resolve/catch paths) and now passes it to
`QiblaSection` only once both `qibla` and `coords` are non-null;
`QiblaSection.tsx` takes a new `coords` prop and forwards it unchanged to
`QiblaCompass`. No new GPS reads, no new permission prompts — `QiblaCompass`
still never fetches location itself, matching the existing centralized-in-
`PrayScreen` pattern.

Files touched: `src/utils/declination.ts` (new), `src/screens/pray/
QiblaCompass.tsx`, `src/screens/pray/QiblaSection.tsx`, `src/screens/pray/
PrayScreen.tsx`, `package.json`/`package-lock.json` (new dependency:
`geomagnetism@0.2.0`, zero transitive deps of its own). Lockfile
regenerated with `npx npm@10 install --package-lock-only` per the npm-10-in-
CI rule; resolved-package count in `package-lock.json` went from 1455 to
1459 (up, not down).

New `__tests__/declination.test.ts` (8 tests): three reproduce NOAA's own
WMM check points straight from `geomagnetism`'s bundled `test/values.csv`
(not hand-picked numbers) — e.g. lat 80°/lon 0° at the 2015.0 epoch has a
documented declination of -3.85°, which this suite's date reconstruction
(same fractional-year-to-ms-offset approach `geomagnetism`'s own test
harness uses) reproduces to within 0.003° in a quick manual check, well
inside the 0.1° `toBeCloseTo` tolerance used in the assertions; two confirm
the sign convention directly (a known-east-declination coordinate pushes
the true heading forward of magnetic, a known-west-declination coordinate
pulls it backward); two cover the 0/360 wraparound in both directions
(magnetic 359.9° plus a small positive declination wraps to just above 0°,
not 360-plus; magnetic 1° plus a negative declination wraps to just under
360°, not negative); one confirms the `date` parameter defaults sanely when
omitted. Full suite: `npx jest --silent` → **13 suites, 98 passed** (was 12
suites, 90 passed — 8 new, nothing existing broken). `npx tsc --noEmit -p .`
clean.

**Not done / not verified here:**
- Not tested against a real device's magnetometer or in a real location —
  this is a software correction to the math only; it depends on
  `react-native-compass-heading` continuing to report true magnetic
  heading (uncorrected) on whatever OS version the device runs, which
  hasn't changed, and on the device's own magnetometer being reasonably
  calibrated, which this fix has no way to detect or influence.
- `geomagnetism`'s current coefficient table (WMM2025) is valid through
  2029-11-13; after that date (or if a user's device clock is set further
  out, which `allowOutOfBoundsModel: true` tolerates with degraded
  accuracy rather than a crash) the declination used is the nearest
  available table's, not an interpolated/forecast one. No action needed
  now — just flagging it as a future upgrade point (bump `geomagnetism`
  when NOAA ships WMM2030).
- No native build (APK/AAB or iOS) was produced or installed to confirm
  `geomagnetism` actually bundles and runs correctly under Metro on-device
  — `tsc` and `jest` both pass, but per the standing rule on verifying
  shipped dependencies, this should be spot-checked on a real build before
  it ships, same as any other new native-adjacent dependency.

## Assets reorganized: by screen, with a shared/ bucket, out of flat dump folders

Per explicit request. `assets/images/`, `assets/map/`, `assets/map2_assets/`,
`assets/characters/`, `assets/animations/` were flat dump folders with no
relationship to the screens that actually use them. Reorganized ~160 files
into `assets/screens/<screen>/...` for single-screen-owned assets (further
split by sub-area where it made sense, e.g. `screens/home/map2/{images,svg}/`,
`screens/gamification/fire/` before its later move -- see below), a
`assets/shared/{icons,mascot,animations,avatars,fire}/` bucket for anything
used by 3+ screens, and `assets/unused/` for files with zero references
anywhere (confirmed via exact-path resolution before moving, not guessed).
`assets/fonts/` was deliberately left untouched -- native-linked by exact
path in `Info.plist`/Android build config, moving it means native config
edits plus a full rebuild to re-verify, well outside a JS-side asset reorg.
`assets/images/playstore-icon.png` also stayed put -- it's a build script's
output target, not a screen asset.

**Method, since this touches ~200 require()/import sites and a wrong one
fails silently (no compile-time error for a bad image path):** wrote a
Node script (not done by hand) that, for every planned move, resolves the
exact relative require() path from every file in `src/` and rewrites only
exact literal matches, then physically moves the file. Ran it in a dry-run
mode first (prints what it would do without touching anything) and checked
reference counts per file against expectations before executing for real.
Caught one real mapping error this way before it happened:
`map/special.png` looked "used" in an earlier broad grep, but that was a
false positive from matching inside `recommended_special.png`'s filename --
the file's own source comments confirm it's dead (byte-identical to
`node_current.png`, intentionally dropped). Moved to `unused/` instead of
guessing it belonged to a screen.

**Caught and fixed a real break the exact-path src/ check couldn't see on
its own**, because the reference lived outside `src/`: `scripts/
generate-android-icons.mjs`, `generate-ios-icons.mjs`,
`generate-notification-icon.mjs`, and `generate-playstore-icon.mjs`
hardcoded paths to `assets/images/lumo_transparent.png` and
`assets/images/lumo_kufi.png` (both now under `assets/shared/mascot/`) as
their source images for generating the app's launcher/notification/store
icons. Updated all four scripts to the new paths and confirmed the source
files exist there.

**Verification, done repeatedly and from multiple independent angles** (per
explicit request to not take this on trust): an exhaustive script resolving
all ~207 `assets`-referencing `require()`/`import` strings in `src/`
against the real filesystem (0 broken, re-run after every change); `tsc
--noEmit` and the full `jest` suite (98/98) re-run after every change; a
repo-wide grep for any leftover old-path string outside `src/` (scripts,
`package.json`, root configs, `android/`, `ios/`, the sibling
`ustadapp-expo/` project). Two independent agents then re-derived and
re-ran all of the above from scratch, without reusing this session's own
scripts or trusting its summary -- both came back clean. One real
classification catch came out of that second pass: `screens/gamification/
fire/` (the streak flame icons) is actually used across gamification,
lesson, home, and shared components -- 5+ screens, well past the
3-screens-shared threshold this reorg was using -- so it was moved again,
to `shared/fire/`, with the same verified rewrite mechanism. Re-verified
clean after that move too.

**Not done, flagged rather than silently skipped:** `assets/screens/
gamification/{redh,halfh,whiteh}.png` (heart icons) are used by both
`HeartsScreen.tsx` and `components/lesson/LessonHeader.tsx` -- two
screens, borderline under the 3+-screens-shared rule. Left under
`gamification/` as a judgment call rather than moved; revisit if a third
consumer shows up. `assets/screens/home/map2/` assets are also used once
by `GemsScreen.tsx` (gamification) outside the map2 subsystem -- same
judgment call, left as-is.

## Pray screen: real compass never matched the approved mockup; salah button wrongly left out

Reported from a real TestFlight build (20053): `QiblaCompass.tsx` had
never been updated to the Figma colors the HTML mockup artifact went
through several rounds of correction to get right (dark navy face with a
white border and a 🕋 emoji -- the component's *original* placeholder

(`#C6D9E7`), bright cyan-blue ring (`#29A4D9`), a proper red/navy
two-tone needle in place of the emoji, tick marks instead of a text "N"

commented out rather than shown-but-disabled; the card's own height was
tuned assuming that button is present, so without it the gold pill at the
bottom was getting visually clipped by the card's rounded corner on a
real device. Restored the button and wired it to `navigation.navigate
('ComingSoon', { title: 'Log Your Salah' })` -- the same "coming soon"
destination the map's Journey/Review buttons already use, rather than a
one-off Alert or a new pattern.

Also: the "enable location" tap only ever re-called the same permission
API, which does nothing visible on a second try once iOS has already
shown its one system dialog and been denied -- the button looked broken
beyond the first attempt. `PrayScreen.tsx` now tracks whether a real
attempt already happened; a retry after an actual denial opens the app's
Settings page (`Linking.openSettings()`) instead of re-asking a dead API.
No UI change beyond that -- same tappable text in `DateRow.tsx`, it just
does something useful every time now, not just the first.

## Black strip at the very bottom of every non-Map tab on iOS

Reported from a real device screenshot (Quests tab): a solid black bar
at the screen's true bottom edge, below the already-correctly-coloured
tab bar. Root cause in `Map2TabBar.tsx`: `bottomClearance` (both the
height reserved for the tab bar AND how far its own light-coloured fill
extends, per `Map2BottomBar.tsx`) was `insets.bottom * 0.55` -- an
unexplained, undocumented fraction of the real home-indicator safe-area
inset. The uncovered remainder sat entirely outside the navigator's own
rendered content, exposing whatever paints behind the whole app at that
point -- the root Stack's dark `contentStyle` (`#0D1B2A`, meant for the
Splash/auth flow), as a flat black strip. Changed to the full
`insets.bottom`, matching the real safe area exactly instead of a
fraction of it.
