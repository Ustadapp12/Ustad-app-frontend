# Changes, 2026-10-13

## iOS recitation always failing ("Scoring failed. Tap the mic to try again")

User (two iPhones, TestFlight 1.0.38, mic access granted): every recitation
submission fails, including after restarting the app.

Evidence: production Vercel logs for `POST /api/v1/progress/speak-attempt`
show every attempt returning 500. Deepgram rejected each upload with
`400 Bad Request: failed to process audio: corrupt or unsupported data`, and
the backend has no handling for that.

Cause: `services/audioRecorder.ts` called `startRecorder()` with no audio
settings. react-native-audio-recorder-player 3.6.14 then records on iOS in
Apple Lossless (ALAC), stereo, 44.1kHz (`avFormat(fromString: nil)` returns
`kAudioFormatAppleLossless` in `ios/RNAudioRecorderPlayer.swift`). Android
defaults to AAC, so only iPhones are affected. Reproduced against Deepgram
with production's exact parameters: the same clip as ALAC m4a gives the
exact error above, and as AAC m4a it transcribes fine. Neither the
Content-Type nor the Sep 30 `mip_opt_out` flag changes either result.

What did NOT change (checked across 1.0.34 to 1.0.38): the recorder wrapper
(last touched Aug 31), the recorder version (3.6.14 in every lockfile), the
upload code, the backend scoring code. Nothing on our side explains it
working a few builds ago; the likely explanation is that Deepgram stopped
decoding ALAC on their end (not provable: the key lacks `usage:read`, and
Vercel log retention is about one day).

Fix (approved by user): `startRecording()` passes
`{ AVFormatIDKeyIOS: 'aac', AVNumberOfChannelsKeyIOS: 1, AVSampleRateKeyIOS: 16000 }`
on both the first attempt and the stuck-recorder retry. The Android keys are
untouched, so Android behaviour is unchanged. Upload MIME stays `audio/m4a`
on iOS; the file is still `sound.m4a`.

Not built yet (user is batching more UI fixes first). Needs verifying on an
iPhone after the next TestFlight build.

Follow-up suggested, not done: backend should catch Deepgram's 400 and return
a 422 ("no audio captured") instead of a 500. That's the user's call to
make and deploy.

## Lesson screen: hint button dead, exercise layout and alignment (user screenshots, 1.0.38)

All approved by the user. Not built yet.

### Hint button did nothing when tapped
Cause: `LessonHeader` floated the hint with `position: 'absolute', top: 50`
inside a header row only ~56pt tall, so almost the whole badge sat outside
its parent's bounds. Touches outside a parent never reach the child on iOS
or Android, and the exercise area (a later sibling) also drew over it: the
speech bubble covered it on audio_fill, the "Try again" banner covered its
label on mistakes_review.
Fix: the hint now sits in a real row of its own under the hearts, right
aligned (`hintRow`). The row keeps its 43pt height on exercise types with
no hint, so content doesn't jump between questions. Special levels (no
hearts) still show it inline in the top row. The tour's cutout and glow
measure this same view, so the tour follows the new position with no
separate change.

### Content anchored to the bottom (recitation dropped onto the mic)
Cause: `ExerciseLayout` used `justifyContent: 'flex-end'` and gave all
leftover space to the top, so each exercise's position depended on its own
height: recitation sat on the mic with a ~230pt empty gap above, audio_fill
rose under the header, and the speech bubble jumped between ~107pt and
~355pt from question to question.
Fix: content is now centred between the header and the footer. It only
moves up when centring would put its bottom under the feedback sheet, never
above the top padding, and never causes scrolling. It's hidden for the
single frame before its height is known, so it doesn't flash at the top
first.

### Fill-blank ayah split into three lines, blank off centre
Cause: the words before the segment, the segment row (with the blank) and
the words after rendered as three stacked blocks, so even a short ayah used
three lines and the blank sat alone on the middle one. Something invisible
next to the blank in its row pushed it ~25pt off centre; most likely an
empty-text token, not confirmed (needs the exercise payload).
Fix: new `components/lesson/AyahWithBlank.tsx` lays the whole ayah out as one
wrapping line in reading order with the blank inline, and drops empty-text
tokens. Used by fill_blank/next_word and audio_fill (which picked "?" for
its audio-only options and still does). The dead `scaledBlankBox` helper and
the old token/blank styles were removed (the sizing logic moved into the
component).

### Three different "Hear" buttons
fill_blank's "Hear words" was small and pinned right, audio_fill's "Hear the
word" was large and centred, read_and_speak's "Hear" was small and centred.
New shared `components/lesson/HearButton.tsx` (one centred pill) replaces all
three, and their three style sets were removed.

### Answer grid narrower than the question card
Options were `minWidth`/`width: '45%'` and centred, leaving a ~13pt inset on
each side. Now `flexBasis: '45%', flexGrow: 1`, so two options plus the gap
span the card's exact width (fill_blank and audio_fill grids).

### Recitation could record the app's own reference audio
Hear buttons were disabled once recording started, but audio already
playing kept playing into the mic, so a learner could tap Hear, then the
mic, and get the reference recitation scored as theirs. The hint modal's
"Hear the Ayah" was never disabled at all.
Fix: `audioPlayer.setPlaybackBlocked()`, set by `audioRecorder` around every
recording: `startRecording()` stops all playback and refuses new playback
(`playAudioUrl`, `resumeAudio`) until `stopRecording()` releases it (in a
`finally`, so a failed stop or an unmount mid-recording also releases it).
One choke point covers every button: word chips, Hear, long-press, the hint
modal. It also stops the per-play iOS `setCategory('Playback')`, and the one
in `preloadAudioUrls`, from switching the audio session out of PlayAndRecord
mid-recording.

Checks: tsc clean, jest 56/56. Not visually verified on a device yet.

## Map speed: memoized nodes, no per-frame scroll JS, lighter assets

User: map is too slow on Samsung (1.0.38 already had the 10-11 split, which
was structural only). Approved items 1 and 2 from the review plus "optimize
each asset" for item 3. No UI or behaviour change intended.

1. Nodes (`MapScreen.tsx`, new `map/components/MapNodeItem.tsx`)
   - `enrichedSections` and `allEnrichedNodes` are `useMemo` (deps: chapter
     layout, `fullLevels`, `firstLevel`), so node objects keep identity
     until data actually changes.
   - New `React.memo` `MapNodeItem` (node + touchable + shake + ayah pill,
     moved as-is). Stable props: `onNodePress` (ref-backed, same pattern as
     `goToChapterStable`), memoized `nodeTagPlacement`, shake interpolation
     memoized per item. A card open / fetch / bounce flip no longer
     re-renders every node.
   - Node key is now `${surahNum}:${surahLevelIdx}` instead of `node.id`, so
     a node no longer remounts when its placeholder id resolves to the real
     lesson_group_id (each surah:level is in exactly one chapter, so unique).
   - Side effect: `firstActiveNode`/`allEnrichedNodes` are now stable, so
     `useRecommendedJump`'s callbacks/effects stop churning every render.
     Effects that matter are id/tick keyed or ref-routed, checked.
2. Scroll
   - `onScroll` Animated.event is memoized (was rebuilt every render).
   - Android: no JS listener at all, scrollY stays purely native.
     iOS keeps a listener only for the bounce flag (`bounces` is iOS-only).
   - Crash breadcrumbs moved to `onScrollEndDrag` / `onMomentumScrollEnd`,
     same half-screen threshold.
3. Assets / memory
   - `MapBackground`: tile 0's grass-seam `<Svg>` cropped from the full 3000dp
     tile to the seam strip (SKY_BOUNDARY_Y to grassPlainTop + sc(8)). The
     plain grass Image covers everything below it, so nothing visible
     changes; react-native-svg backs each Svg with a full-size bitmap, so
     this drops roughly 30+MB on a 1080p phone.
   - Resized to ~3x their max drawn size (decoded memory):
     start.png 1178x1920 -> 239x390 (9.05 -> 0.37MB), birds.png 1024x683 ->
     384x256 (2.80 -> 0.39MB), NEXT_STAGE 678x767 -> 424x480, PREVIOUS_STAGE
     692x756 -> 432x472, recommended_special 447x470 -> 290x305, special_done
     481x503 -> 260x272. Aspect ratios kept. Total ~14MB less decoded.
     Stale committed `android/.../drawable-mdpi/assets_start.png` and
     `assets_birds.png` synced to the new files. Originals backed up in the
     session scratchpad.
   - Not touched: lumo_kufi (used app-wide incl. splash), mountains_crop
     (pad fraction is tied to its pixel height), road brick Svg tiles (still
     the biggest memory user; needs a Skia/sprite rewrite to fix properly).

Verified: tsc clean, eslint = the 1 pre-existing error (unused TOP_MARGIN),
jest 56/56, `react-native bundle` android release builds. NOT yet run on the
emulator or a device; not built.

## iOS 20047: "Could not start recording" (regression from today's AAC fix)

User on iPhone, build 20047: recitation no longer records at all ("Could
not start recording"). Cause: the AAC settings shipped in 20047 (16kHz mono,

  reset kept). All AAC, never ALAC. Android unchanged in behaviour (same
  settings tried twice = the old reset-and-retry).
- Replaces the 32kbps/16kHz attempt committed earlier (b2bcb59, never built).

## Map came back from a level pulled down, Lumo above the mountain

User: on returning from a level the map is "swiped below" with the Lumo
loading shown above the mountain, fixed once they scroll.

Cause (code reading, iPhone not available to reproduce): the automatic
reload on app-foreground (`AppState` -> `handleRefresh`) set the same
`refreshing` state that drives the native `RefreshControl`. Setting it from
code makes iOS pull the ScrollView down ~60pt as if the user had pulled,
which exposes `PullRefreshIndicator` (Lumo + rainbow) above the mountain.
Anything that makes the app briefly inactive during a lesson (a system
prompt etc.) ran that refresh while the map sat under the lesson screen,
and iOS often doesn't restore the offset when the refresh ends off screen,
so the map stayed pulled down until scrolled.

- `useMapData.ts`: `refreshing` is now only a user pull (RefreshControl);
  the foreground reload sets a separate `silentRefreshing`. Exposes
  `reloading` = either.
- `MapScreen.tsx`: loading bar and the reload overlay (star loader) follow
  `reloading`; `RefreshControl` and `PullRefreshIndicator` follow only
  `refreshing`, so code never pulls the map down any more.

tsc clean, jest 56/56; eslint: only the pre-existing exhaustive-deps error
at the first-load effect (present in HEAD). Not built, iOS-only symptom.
