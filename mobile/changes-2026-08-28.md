# Changes — 2026-08-28

Three reported defects. Two of them turned out to share a root cause.

## 1. The "Begin/Continue here!" tag moved the node it belonged to

**Cause.** Every node is pinned by an absolutely positioned wrapper at
`{ left: node.x, top: node.y }` (`MapScreen.tsx`, node render). Inside it,
`MapNode` renders into `S.nodeWrapper`, a plain centered column, and the tag
was an **in-flow child rendered before the node** with `marginBottom: sc(8)`.
So the one node carrying a tag was pushed down by tag height + 8px while every
other node sat exactly at its own `node.y` — and since the road is drawn to
`node.x/node.y`, the recommended node also drifted off the path.

**Fix.** The tag is now absolutely positioned beside the node and out of flow:

- New `S.nodeTagWrap` (`position: 'absolute'`, `top: 0`, `height: NODE_SIZE`,
  `justifyContent: 'center'`) plus `nodeTagWrapRight` / `nodeTagWrapLeft`.
  With the tag out of flow, `nodeWrapper`'s only in-flow child is the node
  itself, so the wrapper box is exactly `NODE_SIZE` tall and the tag centres on
  the node's true vertical middle without anything having to be measured.
- `nodeTag` lost `marginBottom` and gained `maxWidth: NODE_TAG_W`.
- New `MapModel.NODE_TAG_W` (`sc(104)`). It is a **cap, not a measurement**:
  the tag is given it as `maxWidth`, so the side-flip test can never disagree
  with what actually renders. Same guarantee `ACTION_CARD_W` gives the card.
- New `nodeTagOnLeft(node)` beside `actionCardPosition`, using the identical
  flip rule. Right of the node is the default; it swaps to the left only when
  the tag would overrun `MAP_W`. Node x-centres are clamped to 0.20–0.74 of
  `MAP_W` by `chapterXFraction`, so the right-hand end of that range genuinely
  does overrun and would otherwise clip the tag off-screen.
- New `tagOnLeft` prop on `MapNode`, decided at the call site (the only place
  that knows both `MAP_W` and the node's x).

Node position is now independent of whether a tag is present.

## 2. Onboarding never asked for a name (email sign-up path)

**Cause.** `OnboardUsername` was only ever reached by an explicit
`navigation.replace('OnboardUsername')` from `SignUpScreen` and `LoginScreen`
— which are the Google and already-verified paths. An email sign-up goes to
`VerifyEmail` instead, and all three of its exits went **straight to
`OnboardAge`**, skipping the name step entirely.

Second gap: `getNextOnboardingScreen()` was typed
`'OnboardAge' | 'OnboardPath' | null` and could never return `OnboardUsername`,
so a resumed onboarding skipped the name too.

**Fix.**
- `VerifyEmailScreen.tsx` — all three exits (the direct one at `:87` and the
  celebration modal's two dismiss paths) now `replace('OnboardUsername')`.
- `utils/storage.ts` — `getNextOnboardingScreen()` returns `'OnboardUsername'`
  for the checkpoint-A / never-started case, so a resumed onboarding starts at
  the top like a fresh one. Return type widened accordingly.
- `OnboardUsernameScreen.tsx` — back button removed. It is now genuinely the
  first onboarding step, and the account already exists by the time it renders,
  so "back" went to `SignUp` and would have stranded an already-registered user.
  Its two now-dead styles were dropped.

`OnboardUsernameScreen` already advances to `OnboardAge`, and `OnboardAge`'s
back button already returns to it, so the rest of the chain was intact.

**Not changed:** checkpoint B (`currentStep` of `path`/`assessment`) still
resumes at `OnboardPath`. Someone at that checkpoint is past the name question,
so re-asking there would re-ask something already answered.

## 3. "Guest" in the leaderboard — same root cause as #2

Real guests were **already excluded**: the query filters
`User.email_verified.is_(True)` and a guest row defaults to `False`. The app
also hard-gates guests from viewing the board.

What was actually showing was a **real, verified user still named "Guest"**.
Guest rows are seeded `display_name = "Guest"` (backend
`app/auth/service.py:221`; `register()` seeds `"Learner"`, Google seeds the real
name). That placeholder is only ever replaced by the onboarding username step's
`PATCH /users/me/name` — the step that was being skipped. So: play as guest →
upgrade → verify email → name step skipped → the row ranks as "Guest".

Fixing #2 stops any new account reaching that state. Per the decision taken this
session, accounts **already** stored as "Guest" are left alone, and no backend
or leaderboard code was changed.

## 4. Profile now shows the username

`OnboardUsernameScreen` called `updateProfileFields({ display_name })`, which
only writes `profile.display_name`. `ProfileScreen` (and the rest of the app)
reads `user.name`. So the name just typed never reached the profile, which kept
showing the email prefix — or "Guest" on a claimed guest row.

Switched to `updateDisplayName(trimmed)`, which patches `user.name` *and*
`profile.display_name` and persists via `setStoredUser`. This is the same store
action `EditProfileScreen` already used, and its doc comment already spelled out
the distinction. On later launches `hydrate()` resolves the name from the server
profile anyway, so the two paths now agree.

## 5. Splash now shows what it is doing

Hydrate plus a cold-started serverless backend can hold the splash for several
seconds, and a motionless splash reads as a hang.

`SplashScreen.tsx` gained a rotating status line under the mascot:
`Loading…` then `Creating your world…` then `Planting the trees…` then
`Preparing your journey…` then `Almost there…`, 1200ms apart, each crossfading
over 200ms.

It **holds on the last message instead of looping**, since a list that cycles
back to "Loading" is exactly what a stuck screen looks like. The advance is
chained off `msgIdx` (a `setTimeout` per step) rather than one interval, so the
fade and the text swap cannot drift apart and it stops cleanly at the end. A
fast launch simply shows the first message and moves on.

# Session 2 — map polish + bottom padding + progression bug

## 1. Levels "done" that were never played, and the next level never opening

**Reported:** on Al-Ikhlas, levels 7 and 8 read as completed (8 with a full
three gold stars) but the review node after them stayed locked. Also that this
"has happened multiple times", and that 8 was being marked done "when it is not
comparatively done".

**Root cause: a boot race, not a backend problem.** The backend is correct: a
group is `available` the moment the previous group is completed
(`service.py:508`), so with 7 and 8 done the review node genuinely is open
server-side.

What goes wrong is on the client:

1. `bootCache.prefetchAll()` is deliberately **not awaited** at the call site,
   so `getCachedRecommended()` can still be `null` when `MapScreen` mounts.
2. `MapScreen`'s mount effect resolves `currentSurah` once, from that null,
   falling back to `mvp_surah_numbers[0]`, and full-fetches the **wrong
   surah's** levels.
3. Nothing ever corrects it. `subscribeRecommended` forces a re-render but
   re-runs no fetch, and the mount effect has `[]` deps.
4. The surah actually on screen is therefore left with only its *first* level,
   which drops it into `enrichedSections`' no-full-data heuristic, and that
   heuristic **fakes every later normal node as completed with a flat 3 stars**
   while leaving every review node at its baseline `locked`.

That is the whole reported symptom, exactly: a node showing gold 3 stars the
user never played (the fake), sitting next to a review node that never opened
(the baseline). It reproduces intermittently because it depends on which lands
first, the screen or the network.

**Fix** (`MapScreen.tsx`): a `surahsNeedingFullLevels` backfill effect. Any
surah in the visible chapter that has no full levels and is either the
recommended one or reads first-level-`completed` gets its real levels pulled
via `bootCache.fetchLevels` (cache-first, in-flight-deduped, writes through to
disk), replacing the guesses with backend truth. A failed fetch leaves the key
unchanged, so the effect cannot loop on it.

The heuristic itself is kept but re-scoped in comment to what it now is: a
stopgap for the frames before the backfill lands, not a permanent answer.

## 2. The "Continue here" tag

Four separate defects, all in the tag beside the recommended node.

- **Truncated to "Conti...".** The tag's wrapper is absolutely positioned at
  `left: NODE_SIZE + gap` inside a parent that is only `NODE_SIZE` wide, so
  Yoga handed it a *negative* available width and it collapsed. The `maxWidth`
  was never the constraint. Fixed by giving the wrapper a real
  `width: NODE_TAG_W` (it overflows the narrow parent, which nothing clips:
  the old truncated pill already drew outside it). `NODE_TAG_W` also went
  `sc(104)` to `sc(118)`, and the label keeps `adjustsFontSizeToFit` as a last
  resort only.
- **Laid on top of the surah-name scroll.** The scroll is anchored to its
  section's *first* node and the recommended node is very often that same node,
  and neither placement knew about the other. `nodeTagOnLeft` (map-edge test
  only) is replaced by `nodeTagPlacement`, which requires a side to both fit
  the map **and** clear that surah's label box; preference right, then left,
  then above. The above-the-node fallback is real and needed: node x-centers
  are clamped to 0.20-0.74 of MAP_W and the scroll always takes the side with
  *more* room, so "the scroll is on the only side that had space" genuinely
  happens.
- **Pointed at a completed node.** When the surah's per-group ids hadn't
  landed, the fallback took `allEnrichedNodes.find(surahNum === ...)`, the
  surah's first node, frequently already golden. Now it takes the first
  `current`/`available`/`pending` node, falling back to the first
  non-completed, and only then to the first node.
- Text is "Continue here" / "Begin here"; the trailing `!` is dropped.

## 3. Open review nodes were blank green tiles

`recommended_special.png` (green + star) is now the art for **every** reachable

## 5. Bottom padding on gesture-nav phones

**Reported:** dead strip under the tab bar, and under Try Again / Next in the
speak-result sheet, on an Oppo F9, but not on a Samsung A5, same build.

**Root cause** (`UstadNavigationBarModule.kt`): the native height read used the
`navigationBars()` inset as its only signal. That inset is **nonzero in gesture
navigation too**: it is the gesture pill's own band, and OEM skins size it
generously. So on a phone whose owner had turned the buttons *off*, the module
still reported a bar and `safeBottomInset` reserved a full button-bar's worth of
padding. Different skins report different gesture insets, which is exactly why
one phone looked right and the one next to it did not.

Fixes:

- Gate on `Settings.Secure "navigation_mode"` (0 = 3-button, 1 = 2-button,
  2 = gesture). Anything other than 0 contributes nothing, and
  `react-native-safe-area-context`'s own value stands. Defaults to 0 if the key
  is missing, so the original 3-button misreport fix stays in force.
- Also return 0 when `isVisible(navigationBars())` is false: a hidden bar needs
  no clearance. This reads actual current state, so a device that ignores the
  immersive-mode request still reports its bar and still gets padded.
- Return **-1**, not 0, when the Activity/DecorView isn't attached yet, so JS
  can tell "couldn't read it" from "read it, there's no bar" and never caches a
  not-yet-knowable 0 on a 3-button device.

`responsive.ts`: the session-long cache becomes a **1 s TTL** plus an
`AppState -> active` clear. Clearing only on `setImmersiveMode` was not enough:
the hide is posted async to the UI thread, so the very next read could still
land before it took effect and re-cache the pre-hide height for the rest of the
session, which is the same stale reading the clear was meant to prevent. A TTL
self-corrects on the next render and also covers the user changing the system
setting while the app is backgrounded. The read is a sub-millisecond JNI hop.

**This needs a native rebuild to take effect.** It is Kotlin, not JS.

## 6. Speak-result sheet (Try Again / Next)

- Base `paddingBottom` 36 to 16, kept separate from `insets.bottom`. 36 was
  chosen when the inset was usually 0; stacked on a real inset it left a dead
  strip tall enough to force scrolling for content that would otherwise fit.
  The gap to the button and the clearance for the system bar are two different
  jobs and only one of them should scale with the device.
- `maxHeight` 65% to 72%.
- CORRECT AYAH / YOU SAID boxes sized to hug their type: `lineHeight` 38 to 34
  on a 22px font (1.73x to 1.55x, still real headroom for Naskh ascenders and
  harakat), `paddingVertical` 12 to 10, label margin 8 to 6, button row margin
  18 to 14.

# Session 3 — no fabricated progress, duplicate exercise, padding sweep

## 1. The map no longer guesses that a level is completed

Standing rule now, not a one-off fix: **nothing may render a completion the
backend has not confirmed.** A node claiming three gold stars for a level the
user never played tells them something false about their own work, and that is
the one failure here that isn't cosmetic.

`enrichedSections`' fallback, for a surah where only the first level has
arrived, was:

    status: 'completed', stars: 3     // a guess

It is now:

    status: 'available', stars: 0, resolved: false

`available` can only be wrong in the harmless direction. It offers a level the
user may already have finished; it never credits them with one they haven't.
The `surahsNeedingFullLevels` backfill added in session 2 then overwrites it
with real backend data, usually within the same second (bootCache is
cache-first over a disk cache).

**This required a second fix to be safe.** An unresolved node's `id` is still
the static layout placeholder (`${surahNum}_${n}`), not a `lesson_group_id` the
backend has ever heard of. Previously that was contained because such nodes
were either inert (`locked`) or routed through the completed-node verify path.
Making them tappable-and-startable would have navigated into `LessonSession`
with a bogus groupId.

So `handleNodePress` now has a resolve step for any `!node.resolved` node on the
start path: fetch the surah's real levels, map by array position (not
`levelNum` — review levels interleave), and act on the real group. If it turns
out `locked`, shake it. If `completed`, show the retry prompt. Otherwise open
the start card with the real id. A failed fetch stays put rather than
navigating somewhere that doesn't exist.

## 2. An exercise being shown again after it was cleared

Two client-side defects, both real, both fixed. One backend finding, reported
only (backend is read-only here).

**The submit lock didn't lock.** `submitAnswer` guarded on `submitting`, which
is React state — two taps landing in the same frame both read it as `false`
before the setter commits, and both fire a formula-attempt for the same
`ex_id`. Replaced with a `submitLockRef` that flips synchronously inside the
first handler, so the second tap in the same frame sees it. Released at all
three points where `submitting` is released.

**`next_exercise` was mounted blind.** The backend answers a stale or duplicate
`ex_id` by returning *its own current exercise* as `next_exercise` — see
`process_answer`'s "ex_id mismatch" resync branch, `session_engine.py:545`. So
that field is not always forward progress, and the client did
`setExercise(result.next_exercise)` unconditionally. Now every answered
`ex_id` goes into `answeredExIdsRef`, and an echo of one is ignored rather than
mounted. This is safe because **the engine never reuses an ex_id** — even a
wrong-answer replay in the review phase is minted a fresh one
(`_build_review_queue`: `replay["ex_id"] = fx._new_id()`), so an id coming back
is always a resync artefact and never real new work. Ignoring it leaves the
current card up rather than rewinding, and nothing deadlocks: the user can
still answer that card and the server moves on. A failed round trip removes the
id again, so a network error doesn't lock the user out of retrying.

### Backend finding — not changed, reported only

`ayah_texts` is built from `ayah_docs` (every ayah in the group, sorted) and
then indexed positionally against a *different* list in two places:

- `formula_exercises.build_base_queue` — `for i, ayah_no in
  enumerate(sorted_ayah_nos)` where `sorted_ayah_nos` comes from
  `ayah_word_map` (word_morphology), then `ayah_texts[i]`.
- `session_engine._build_review_queue` — `for i, ayah_no in
  enumerate(ayah_nos)` where `ayah_nos` comes from `state["word_map"]`, then
  `ayah_texts[i]`.

Those two lists only stay aligned while every ayah in the group has
word_morphology rows. An ayah present in `ayah_docs` but missing from the word
map shifts the index, and a recite-aloud card for ayah 2 then renders ayah 1's
text — the first ayah appearing a second time, under the wrong label. It would
be intermittent and surah-specific, which fits "sometimes". Not touched, per
the read-only rule on the backend.

## 3. Bottom padding, swept app-wide

Audited every bottom-edge calculation in the app. Every `insets.bottom`
consumer routes through `safeBottomInset` — the five files that use
`useSafeAreaInsets` without it (`GuestGate`, `MapScreen`, `DailyQuestScreen`,
`SplashScreen`, `TourLessonScreen`) read only `insets.top`, so nothing bypasses
the corrected path. With session 2's native fix in place there is no remaining
route by which a gesture-nav phone reserves button-bar padding.

The base spacing stacked on top (`+12`, `+16`, `+24`, `+32` on the various
screens, `TAB_BAR_CONTENT_H = 80` / `TAB_BAR_PAD_BOTTOM = 16` on the tab bar)
is ordinary design spacing and was left alone; it is not the dead strip.

**Still requires a native rebuild.** The padding fix is Kotlin. It cannot
appear in a Metro reload, and it has to be verified from the built artifact,
not from the source.
